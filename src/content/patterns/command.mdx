## How it works

A menu action, a keyboard shortcut, and an undo history may all need to invoke the same edit. None of them should contain the code that changes the document.

Command packages the edit with its receiver and arguments. `AppendText` knows which document to change and what to append. `History` knows how to execute commands and undo the most recent one, without knowing how an append works.

## Why use it

Buttons, queues, and undo histories should not each implement document editing. Storing only callbacks may also omit the state needed to reverse an operation. A command separates who requests an action from the receiver that performs it.

## Practical use cases

1. Editor actions with undo support.
2. Queued application operations with explicit parameters.
3. UI actions invoked from menus, buttons, or keyboard shortcuts.
4. Batch or macro operations that reuse the same invocation contract.

## Java walkthrough

### 1. Separate the edit from the document

`Document` owns the text. `AppendText` owns an addition and the information needed to reverse its application.

### 2. Track whether the command is applied

On execution, the command saves the previous text and computes the expected result. Applying the same command again before undo is an error.

### 3. Record successful commands

`History.execute()` pushes the command after execution returns. If execution throws, the history does not claim the command succeeded.

### 4. Undo the most recent edit

History peeks before undoing and pops only after success. The append checks the current text against its expected result so it does not overwrite an obvious external edit.

For example:

```java
Objects.requireNonNull(command).execute(); commands.push(command);
```

## Extension exercise

Add redo with a second stack. Clear redo when a new successful edit branches history. For production collaborative editing, replace whole-text equality with an explicit version or operation model; matching text alone cannot detect an edit-away-and-back sequence.

## Verification

`CommandChecks.java` covers lIFO reversal, empty undo, re-execution after undo, duplicate application rejection, external-edit detection, and retaining valid history when execution or undo fails.

```bash
cd examples/command
javac --release 21 CommandDemo.java CommandChecks.java
java CommandChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Decoupling | Invokers become generic while command types and lifecycle rules grow. |
| Undo | Not every action is reversible; compensating a remote action is a separate domain operation. |
| Failures | A failing execute may already have side effects; the interface alone cannot supply atomicity. |

This is a single-threaded in-memory editor with no persistence. Undo stores whole text, so large documents cost memory. It expects edits to go through the history; it does not implement distributed undo, transactions, or guaranteed reversal of arbitrary external side effects.

## Choosing this pattern

A command is useful when requests need to travel through menus, queues, histories, or batches. Undo adds a second set of obligations: what state is saved, who can edit the receiver, and what happens when reversal fails? Some actions need compensation rather than literal undo.
