## The idea in plain English

Command turns an operation into an object containing the information needed to execute it. An append command knows its document and text. A history invokes commands and can ask the latest one to undo itself without knowing the document-edit details.

> Command does not require undo. If undo is offered, define receiver ownership, failure behavior, and reversibility explicitly.

## The problem before the pattern

Buttons, queues, and undo histories should not each implement document editing. Storing only callbacks may also omit the state needed to reverse an operation. A command separates who requests an action from the receiver that performs it.

## Practical use cases

1. Editor actions with undo support.
2. Queued application operations with explicit parameters.
3. UI actions invoked from menus, buttons, or keyboard shortcuts.
4. Batch or macro operations that reuse the same invocation contract.

## Java walkthrough

### 1. Separate receiver and operation

Document owns text. AppendText owns the request and snapshots around that request.

### 2. Execute with lifecycle checks

The command rejects applying itself twice without undo. It saves prior text and records its expected post-edit text.

### 3. Record only successful execution

History pushes after execute returns. A failing command is not added to the undo stack.

### 4. Undo conservatively

History peeks first and removes only after a successful undo. AppendText rejects undo if the receiver text differs from the expected result.

## Extension exercise

Add redo with a second stack. Clear redo when a new successful edit branches history. For production collaborative editing, replace whole-text equality with an explicit version or operation model; matching text alone cannot detect an edit-away-and-back sequence.

## Verification

CommandChecks.java verifies: LIFO reversal, empty undo, re-execution after undo, duplicate application rejection, external-edit detection, and retaining valid history when execution or undo fails.

```bash
cd examples/command
javac --release 21 CommandDemo.java CommandChecks.java
java CommandChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Decoupling | Invokers become generic while command types and lifecycle rules grow. |
| Undo | Not every action is reversible; compensating a remote action is a separate domain operation. |
| Failures | A failing execute may already have side effects; the interface alone cannot supply atomicity. |

This is a single-threaded in-memory editor with no persistence. Undo stores whole text, so large documents cost memory. It expects edits to go through the history; it does not implement distributed undo, transactions, or guaranteed reversal of arbitrary external side effects.
