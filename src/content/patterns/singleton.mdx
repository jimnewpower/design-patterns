## How it works

Singleton provides one instance and a place to obtain it. In Java, that promise has a scope: a class loaded by one defining class loader has its instance; another class loader or JVM may have another.

The example uses a one-constant enum for a read-only report-format catalog. Startup obtains the instance and injects it into `ReportNamer`. The consumer gets an ordinary dependency, so its tests can still supply a fake.

## Why use it

Constructing a new object at every call site can duplicate state or resource ownership:

```java
// Illustrative API: each caller independently creates its catalog.
FormatCatalog first = new DefaultFormatCatalog();
FormatCatalog second = new DefaultFormatCatalog();
```

A naive lazy Singleton is worse under concurrency:

```java
// Deliberately broken: two threads can both observe null.
if (instance == null) instance = new Catalog();
return instance;
```

Two threads can both pass the null check, and the assignment provides no safe-publication protocol. The enum version uses Java’s class-initialization rules to coordinate creation and publication.

Multiple copies of this immutable catalog would work correctly. It is a small example of the mechanism, not a reason to require a Singleton in a real reporting application.

## Practical use cases

1. **Runtime environment access:** expose the application’s runtime integration through one controlled object, as Java’s `Runtime` API does.
2. **Fixed read-only catalogs:** share stable lookup data when one catalog per application scope is the chosen policy.
3. **In-process coordination:** centralize ownership of a process-local registry or coordinator when competing owners would be incorrect. Its mutable operations still require their own concurrency design.
4. **Application-wide infrastructure ownership:** manage one resource manager in a defined application scope, with an explicit shutdown policy. A dependency-injection container is often a better owner than a global accessor.

“One connection”, “one user session”, and “one active job” usually describe different scopes and should not be collapsed into a process-wide Singleton. Multiple services or JVMs need an external coordination mechanism if the requirement is distributed uniqueness.

## Java walkthrough

### 1. Define the consumer-facing interface

```java
interface FormatCatalog {
    String extensionFor(String format);
}
```

A consumer needs lookup behavior, not knowledge of how the implementation is instantiated.

### 2. Implement a single-constant enum

```java
enum ReportFormats implements FormatCatalog {
    INSTANCE;
    private final Map<String, String> extensions = Map.of("text", ".txt", "html", ".html");

    @Override
    public String extensionFor(String format) {
        Objects.requireNonNull(format, "format");
        String extension = extensions.get(format.toLowerCase(Locale.ROOT));
        if (extension == null) throw new IllegalArgumentException("Unsupported format: " + format);
        return extension;
    }
}
```

The enum declares one instance. Java class initialization coordinates its construction and publication. Ordinary callers cannot create extra enum constants with `new`.

Concurrent lookups are safe because the map and its string contents are immutable. Adding a mutable map or counter would require a separate concurrency decision.

`Locale.ROOT` keeps case normalization independent of the host’s default locale. Unknown formats, including blank strings, fail instead of silently choosing a default.

### 3. Inject the dependency into a client

```java
static final class ReportNamer {
    private final FormatCatalog catalog;
    ReportNamer(FormatCatalog catalog) {
        this.catalog = Objects.requireNonNull(catalog, "catalog");
    }
    public String fileName(String baseName, String format) {
        Objects.requireNonNull(baseName, "baseName");
        if (baseName.isBlank()) throw new IllegalArgumentException("Base name must not be blank");
        return baseName + catalog.extensionFor(format);
    }
}
```

The client has no global lookup. Tests can provide a fake `FormatCatalog`; production can supply the Singleton.

### 4. Wire once at startup

```java
FormatCatalog catalog = ReportFormats.INSTANCE;
ReportNamer namer = new ReportNamer(catalog);
String name = namer.fileName("engineering-tools", "HTML");
```

This produces `engineering-tools.html`. The example composes names only; it performs no file I/O and is not a filesystem-path validation utility.

## Runtime scope and concurrency

<SingletonDiagrams kind="runtime" />

For an application class like this enum, instance uniqueness is tied to the class identity established by its defining class loader. Multiple class loaders can independently define the same named class; separate JVMs also have separate instances. Avoid calling it “one object everywhere”.

Java class initialization provides coordinated initialization and safe publication. Later operations on mutable state require additional synchronization or suitable concurrent structures. Even a concurrent collection does not make a multi-step business operation atomic automatically.

The enum initializes when the class is initialized, normally at first active use such as accessing `INSTANCE`. It is not necessarily constructed at JVM startup. Class initialization failure can make subsequent uses fail too, so avoid slow, fallible network or file operations inside a global instance initializer.

## Alternatives in Java

| Implementation | Useful property | Responsibility or tradeoff |
| --- | --- | --- |
| Single-constant enum | Concise; enum serialization preserves constant identity | Fixed instance set and no ordinary class inheritance. |
| Static final field | Simple initialization under Java’s class-initialization rules | A class-based implementation must separately consider serialization and construction bypasses. |
| Initialization-on-demand holder | Defers the instance until holder initialization | More code; still scoped to class identity. |
| Synchronized accessor | Straightforward serialization of access | Locking on each access; usually unnecessary for a fixed instance. |
| Double-checked locking | Can avoid most accessor locking | Requires correct `volatile` publication and careful implementation; often needless complexity. |

A class-based holder looks like this:

```java
final class CatalogService {
    private CatalogService() { }
    private static final class Holder {
        private static final CatalogService INSTANCE = new CatalogService();
    }
    static CatalogService instance() { return Holder.INSTANCE; }
}
```

Java initializes the nested holder when it is first actively used. This is a class-based alternative to the enum. Its private constructor controls ordinary construction; reflection and serialization need separate consideration.

For the enum, Java’s serialization mechanism resolves the named constant rather than reconstructing a new independent enum instance. That preserves identity, but does not turn enum serialization into a snapshot of mutable application state.

## Testability and dependency injection

```java
FormatCatalog fake = format -> ".test";
ReportNamer namer = new ReportNamer(fake);
```

This isolates client behavior without mutating global configuration or introducing a reset method on the Singleton. Calling `ReportFormats.INSTANCE` inside every service would hide the dependency and couple tests to process-wide lifetime.

A container-managed singleton usually means one instance per relevant container or bean definition, rather than the GoF class enforcing its own uniqueness. You can often get the needed reuse by constructing an ordinary object once and injecting it. Prefer that when tests, multiple configurations, or explicit shutdown ownership matter more than enforced instance restriction.

## Extend it: a new format and a usage counter

First add `"markdown", ".md"` to the immutable catalog and check the generated filename. The consumer does not need to change.

Then consider adding a request counter. An ordinary `int` increment would introduce shared mutable state and a race. If you choose `AtomicLong`, define whether counts are global across all consumers and how tests avoid assuming a fresh zero value. Do not add a public reset merely to make tests convenient.

**Exercise:** instead implement a counter as an ordinary injected object and give each test a fresh instance. Compare its lifecycle and test isolation with the Singleton version. Is global counting actually required?

## Verification

`SingletonChecks.java` checks:

- Concurrent first access by 32 virtual-thread tasks, all observing the same instance and valid lookup data.
- Identity preservation across a local enum serialization round trip.
- Filename output, case normalization, and invalid inputs.
- Consumer replacement with an injected fake.

```bash
cd examples/singleton
javac --release 21 SingletonDemo.java SingletonChecks.java
java SingletonChecks
```

The concurrency check starts before the main thread actively uses the enum, coordinates workers with latches, uses bounded waits, and cancels tasks during cleanup. No timing sleeps are used. Run it in a fresh JVM to exercise first use again.

The concurrent test is a useful regression check. The safety guarantee comes from Java’s initialization rules, not from running a finite number of threads.

## Tradeoffs and common mistakes

| Concern | What to decide |
| --- | --- |
| Global lifetime | Does the dependency really need that scope? |
| Hidden dependencies | Prefer explicit injection into business code. |
| Mutable state | Define synchronization and atomic operation boundaries. |
| External resources | Define startup, failure, shutdown, and ownership explicitly. |
| Multiple deployments | A JVM-local Singleton cannot coordinate replicas. |
| Test isolation | Avoid mutable global settings and reset-driven tests. |

Do not use Singleton merely because creating an object is inconvenient. Do not equate one instance with thread safety, or a final reference with immutable reachable state. Avoid unbounded caches and request-specific data living for the application’s entire lifetime.

## Related patterns

| Approach | Central concern | Compared with Singleton |
| --- | --- | --- |
| Dependency injection | Supplying dependencies and controlling lifetime | Can reuse one ordinary object without a global access point. |
| Static utility | Stateless operations without an instance | Has no object identity to inject or replace. |
| Abstract Factory | Related product families | A factory may have a singleton lifetime, but that is independent of its creation role. |
| Prototype | Creating copies of configured objects | Expands instance count instead of restricting it. |
| Facade | Simplifying subsystem access | May have any lifetime; a single access interface does not imply one instance. |

## A Java API connection

Java’s `Runtime.getRuntime()` exposes the runtime object associated with the application. Its API explicitly documents a single instance and prevents application construction of another. It is a useful example of a lifetime requirement built into the API.

## Choosing this pattern

Creating one object at startup and passing it to consumers is often all an application needs. Enforce a Singleton only when additional instances would be wrong. Keep request-specific state out of it, and define who owns shutdown if the instance holds external resources.
