## The idea in plain English

Composite lets clients treat a single object and a group of objects through the same interface. A part has a mass; an assembly also has a mass, computed from its children. The client asks grams() without deciding whether it received a leaf or a group.

> Define whether your model is a tree, a graph, or placements in a graph before choosing traversal and aggregation rules.

## The problem before the pattern

A client that checks each object type and manually drills into nested lists duplicates traversal logic. Every new nesting level or leaf type can require another special case. Put the common operation on Component and let a group delegate recursively.

## Practical use cases

1. Parts and nested assemblies in a bill of materials.
2. Files and folders with aggregate sizes.
3. UI widgets and container layouts.
4. Task groups with aggregate effort estimates.

## Java walkthrough

### 1. Define the common operation

The sealed Component interface lists the permitted immutable implementations. All masses are integral grams represented as long.

### 2. Validate a leaf

Part rejects negative masses and null names. Its record accessor directly implements grams().

### 3. Aggregate children

Assembly snapshots its child list and recursively adds each child mass. Math.addExact rejects overflow instead of silently wrapping.

### 4. Build the tree

main nests an Electronics assembly inside a Sensor. The same grams() call works for either node.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
for (Component child : children) total = Math.addExact(total, child.grams());
```

## Extension exercise

Add a recursive leaf-count operation. Decide whether it belongs on Component or in a Visitor. If modeling a BOM graph with reused subassemblies, define whether each placement contributes mass independently. Do not deduplicate by object identity unless that matches the domain.

## Verification

CompositeChecks.java verifies: Nested totals, empty assemblies, defensive copying, unmodifiable children, rejection of invalid leaves and null children, and explicit arithmetic overflow.

```bash
cd examples/composite
javac --release 21 CompositeDemo.java CompositeChecks.java
java CompositeChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Uniform operation | Clients stay simple, but leaf and group semantics must be coherent. |
| Tree invariants | Immutability makes normal cyclic construction unavailable; mutable graphs need cycle policy. |
| Growing operations | Adding operations to Component affects both implementations; Visitor may fit a stable tree with many operations. |

This is an immutable tree. It does not model physical tolerances, units conversion, cyclic product graphs, or concurrent editing. A reusable object can occur in multiple child positions and its mass counts once per placement. Very deep recursion can exhaust the call stack.

| Approach | Distinction |
| --- | --- |
