## How it works

A housing has a mass. So does an assembly containing that housing, a board, and a cable. A caller should be able to ask either object for its mass without writing a different traversal for each nesting level.

Composite gives parts and assemblies the same interface. A part returns its stored mass; an assembly asks its children and adds their results.

## Why use it

A client that checks each object type and manually drills into nested lists duplicates traversal logic. Every new nesting level or leaf type can require another special case. Put the common operation on Component and let a group delegate recursively.

## Practical use cases

1. Parts and nested assemblies in a bill of materials.
2. Files and folders with aggregate sizes.
3. UI widgets and container layouts.
4. Task groups with aggregate effort estimates.

## Java walkthrough

### 1. Put mass on the common interface

Both `Part` and `Assembly` implement `Component.grams()`. Mass is a nonnegative `long` measured in integral grams throughout this example.

### 2. Keep the leaf simple

A `Part` stores its mass. The record constructor rejects negative values and null names; its generated accessor supplies the common operation.

### 3. Let the group ask its children

`Assembly` copies the child list. Its `grams()` method calls the same operation on each child and sums the results with `Math.addExact`, which throws on overflow.

### 4. Use the root like any other component

The Sensor contains a Housing and an Electronics assembly. The client asks the Sensor for its mass without knowing how many levels it contains.

For example:

```java
for (Component child : children) total = Math.addExact(total, child.grams());
```

## Extension exercise

Add a recursive leaf-count operation. Decide whether it belongs on Component or in a Visitor. If modeling a BOM graph with reused subassemblies, define whether each placement contributes mass independently. Do not deduplicate by object identity unless that matches the domain.

## Verification

`CompositeChecks.java` covers nested totals, empty assemblies, defensive copying, unmodifiable children, rejection of invalid leaves and null children, and explicit arithmetic overflow.

```bash
cd examples/composite
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Uniform operation | Clients stay simple, but leaf and group semantics must be coherent. |
| Tree invariants | Immutability makes normal cyclic construction unavailable; mutable graphs need cycle policy. |
| Growing operations | Adding operations to Component affects both implementations; Visitor may fit a stable tree with many operations. |

This is an immutable tree. It does not model physical tolerances, units conversion, cyclic product graphs, or concurrent editing. A reusable object can occur in multiple child positions and its mass counts once per placement. Very deep recursion can exhaust the call stack.

## Choosing this pattern

Use a common interface when an operation makes sense for both a leaf and a group. Then settle the structure rules: are children owned, can a subassembly appear twice, and is the model a tree or a graph? Those answers determine how totals and traversal should behave.
