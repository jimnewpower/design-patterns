## How it works

An undo history needs to remember earlier editor state. It should not have to know every field in the editor, or how those fields must agree.

With Memento, the editor creates a snapshot and later restores it. History holds the snapshot without reading its contents. Adding a field changes the editor’s snapshot logic rather than every place that stores checkpoints.

## Why use it

If history reads and writes all editor fields directly, it becomes coupled to internal representation and can restore only part of the state. A snapshot owned by the editor centralizes what constitutes a consistent saved state.

## Practical use cases

1. Editor checkpoints and undo.
2. Restoring a configuration after a canceled edit.
3. Pausing a simulation configuration before speculative changes.
4. In-memory recovery points in a transactional interaction.

## Java walkthrough

### 1. Update the editor consistently

`Editor.set()` checks the title and copies the tool list before assigning either field. A failed edit leaves the old state intact.

### 2. Let the editor capture its state

`save()` creates a `Snapshot` containing the title, an immutable tool list, and the owning editor. Snapshot contents are private.

### 3. Keep history out of the saved fields

`History` stores snapshots on a stack. It asks the editor to save or restore them; it never reads the title or tools itself.

### 4. Restore a checkpoint

The editor rejects another editor’s snapshot. History removes a checkpoint only after restoration succeeds.

For example:

```java
editor.restore(snapshots.peek()); snapshots.pop(); return true;
```

## Extension exercise

Add redo and a bounded history policy. Estimate storage when snapshots include large structures, and consider immutable structural sharing before copying large graphs. Add a new editor field and test that restoration includes it rather than silently omitting it.

## Verification

`MementoChecks.java` covers multiple checkpoints in LIFO order, empty history, input snapshot isolation, repeatable restore, rejection of another editor’s snapshot, and failed edits preserving current state.

```bash
cd examples/memento
javac --release 21 MementoDemo.java MementoChecks.java
java MementoChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Encapsulation | Originator owns snapshot content, reducing caretaker coupling. |
| Memory | Whole-state history can grow without bound; define retention. |
| Consistency | Mutable nested fields need copying or immutable ownership, not just a new outer snapshot object. |

Snapshots are in-memory and keep an owner reference; they are not a durable or versioned serialization format. All types are nested for a single-file demo; the caretaker respects the opaque API by convention. There is no concurrency or external-resource restoration. A checkpoint is made before an edit and undone by restoring that checkpoint.

## Choosing this pattern

Snapshots are useful when restoration belongs to the object that owns the state. Set a history limit before snapshots become large. For durable checkpoints, define a versioned format; an in-memory object graph is not a persistence scheme.
