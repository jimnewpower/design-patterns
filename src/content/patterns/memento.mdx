## The idea in plain English

Memento captures an object’s state so that the same object can later restore it without exposing its representation to the caretaker. An editor saves title and tool data in a snapshot; history stores that opaque snapshot and requests restoration on undo.

> A memento is meaningful only if it captures a consistent state and clearly belongs to an originator and lifetime.

## The problem before the pattern

If history reads and writes all editor fields directly, it becomes coupled to internal representation and can restore only part of the state. A snapshot owned by the editor centralizes what constitutes a consistent saved state.

## Practical use cases

1. Editor checkpoints and undo.
2. Restoring a configuration after a canceled edit.
3. Pausing a simulation configuration before speculative changes.
4. In-memory recovery points in a transactional interaction.

## Java walkthrough

### 1. Validate before assignment

Editor.set validates title and copies tools before changing either field, avoiding partial state on a failed edit.

### 2. Capture a snapshot

save creates an immutable Snapshot tied to that editor. Immutable strings and the copied list keep saved data stable.

### 3. Store opaque history

History keeps snapshots in a stack. Its code never reads the saved title or list.

### 4. Restore owned state

restore rejects snapshots from another editor. History pops only after restore succeeds.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
editor.restore(snapshots.peek()); snapshots.pop(); return true;
```

## Extension exercise

Add redo and a bounded history policy. Estimate storage when snapshots include large structures, and consider immutable structural sharing before copying large graphs. Add a new editor field and test that restoration includes it rather than silently omitting it.

## Verification

MementoChecks.java verifies: Multiple checkpoints in LIFO order, empty history, input snapshot isolation, repeatable restore, rejection of another editor’s snapshot, and failed edits preserving current state.

```bash
cd examples/memento
javac --release 21 MementoDemo.java MementoChecks.java
java MementoChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Encapsulation | Originator owns snapshot content, reducing caretaker coupling. |
| Memory | Whole-state history can grow without bound; define retention. |
| Consistency | Mutable nested fields need copying or immutable ownership, not just a new outer snapshot object. |

Snapshots are in-memory and keep an owner reference; they are not a durable or versioned serialization format. All types are nested for a single-file demo; the caretaker respects the opaque API by convention. There is no concurrency or external-resource restoration. A checkpoint is made before an edit and undone by restoring that checkpoint.
