## The idea in plain English

Proxy stands in for another object behind the same interface and controls access to it. A lazy document proxy can exist before its stored document is loaded. On first read it obtains the real document, then delegates subsequent reads to it.

> A proxy changes when or whether access occurs; document those differences rather than promising perfect transparency.

## The problem before the pattern

Loading every report at startup may be unnecessary and expensive. Putting lazy checks throughout callers repeats lifecycle logic. A proxy lets callers keep using Document while one wrapper owns initialization policy.

## Practical use cases

1. Virtual proxies that load expensive content on demand.
2. Protection proxies that check authorization before access.
3. Remote proxies that represent a service boundary.
4. Access-control or caching wrappers with a deliberately preserved contract.

## Java walkthrough

### 1. Preserve the subject contract

Both document types implement read. Callers need not branch on whether loading has occurred.

### 2. Accept a loader

LazyDocument stores a Supplier and leaves its delegate empty at construction.

### 3. Initialize on demand

A synchronized read initializes exactly once after a successful load. A throwing or null-producing loader leaves the delegate empty.

### 4. Delegate subsequent access

Once initialized, read uses the same delegate. The monitor also serializes delegate reads in this intentionally simple design.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
if (delegate == null) delegate = Objects.requireNonNull(loader.get(), "Loaded document");
```

## Extension exercise

Add a protection proxy requiring an authorization predicate, and decide whether permission is checked per access or only before loading. Test revoked access explicitly. Do not assume loading once means authorization remains valid forever.

## Verification

ProxyChecks.java verifies: No eager load, concurrent callers sharing one successful load, repeated reads, failed-load retry, and null loader/result rejection.

```bash
cd examples/proxy
javac --release 21 ProxyDemo.java ProxyChecks.java
java ProxyChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Transparency | Preserve results and meaningful exceptions even while changing access timing. |
| Concurrency | Synchronized loading is simple but can serialize slow operations. |
| Lifecycle | Define ownership, invalidation, refresh, and cleanup if the real subject owns resources. |

This is a virtual proxy, not a remote client or security boundary. Reads hold a lock while loading and delegating, which is simple but can block callers. The loader must not recursively call this same proxy. Retry after failure is explicit policy, not exactly-once external execution.
