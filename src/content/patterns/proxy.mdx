## How it works

A report can appear in a catalog before anyone opens its content. Loading every document immediately would do work that many users never need.

A lazy proxy implements the same `Document` interface as the loaded document. It loads the real object on the first read, then delegates later reads to it. Callers keep using `read()`; the proxy owns the loading decision.

## Why use it

Loading every report at startup may be unnecessary and expensive. Putting lazy checks throughout callers repeats lifecycle logic. A proxy lets callers keep using Document while one wrapper owns initialization policy.

## Practical use cases

1. Virtual proxies that load expensive content on demand.
2. Protection proxies that check authorization before access.
3. Remote proxies that represent a service boundary.
4. Access-control or caching wrappers with a deliberately preserved contract.

## Java walkthrough

### 1. Use the same interface on both sides

`StoredDocument` and `LazyDocument` both implement `Document.read()`. The client can hold either one.

### 2. Defer the work

The proxy constructor stores a loader. It does not call it, so creating the proxy does not load document content.

### 3. Load on the first read

`read()` is synchronized. A successful load fills the delegate field; a thrown exception or null result leaves it empty so a later read can try again.

### 4. Reuse the loaded document

Later reads delegate to the stored object. The lock also serializes those reads, which keeps this implementation simple but may limit throughput for a slow delegate.

For example:

```java
if (delegate == null) delegate = Objects.requireNonNull(loader.get(), "Loaded document");
```

Add a protection proxy requiring an authorization predicate, and decide whether permission is checked per access or only before loading. Test revoked access explicitly. Do not assume loading once means authorization remains valid forever.

## Verification

`ProxyChecks.java` covers no eager load, concurrent callers sharing one successful load, repeated reads, failed-load retry, and null loader/result rejection.

```bash
cd examples/proxy

```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Transparency | Preserve results and meaningful exceptions even while changing access timing. |
| Concurrency | Synchronized loading is simple but can serialize slow operations. |
| Lifecycle | Define ownership, invalidation, refresh, and cleanup if the real subject owns resources. |

This is a virtual proxy, not a remote client or security boundary. Reads hold a lock while loading and delegating, which is simple but can block callers. The loader must not recursively call this same proxy. Retry after failure is explicit policy, not exactly-once external execution.

## Choosing this pattern

Use a proxy when loading, authorization, remote access, or another access policy should be handled in one place. Document the timing and failure behavior callers will notice. A lazy proxy that retries failed loads has a different contract from one that caches the failure.
