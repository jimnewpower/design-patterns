## How it works

Two import jobs may share almost their entire workflow: read the values, normalize them, validate them, and return the completed list. One keeps the supplied case; the other converts names to uppercase.

Template Method keeps that sequence in a superclass. Subclasses supply the normalization step, while the shared `run()` method controls when each step happens.

## Why use it

Two import variants may duplicate input iteration, validation, and completion handling while differing only in normalization. Copying the algorithm creates drift. Keep the order in one final method and override only the variation points.

## Practical use cases

1. Import pipelines with common validation and variant normalization.
2. Framework lifecycle algorithms with controlled extension hooks.
3. Test or build workflows with a fixed sequence and specialized steps.
4. Report generation where the assembly order is stable but selected phases vary.

## Java walkthrough

### 1. Keep the sequence in one method

`run()` copies the input, normalizes and validates each value, and produces an immutable result. It is final so subclasses cannot reorder those steps.

### 2. Require the normalization step

`normalize()` is abstract. One subclass trims input; the other trims and converts it to uppercase using `Locale.ROOT`.

### 3. Provide defaults for the other hooks

`validate()` rejects blank values. `afterImport()` does nothing unless overridden, and runs only after every item has passed validation.

### 4. Call the template from the client

The client invokes `run()` on either subclass. Both follow the same workflow, even though the resulting names differ.

For example:

```java
String normalized = java.util.Objects.requireNonNull(normalize(value));
validate(normalized); result.add(normalized);
```

## Extension exercise

Add a subclass that rejects duplicate normalized names. Decide whether duplicate validation belongs in a new whole-list step rather than an item step. Test that the completion hook is skipped when that validation fails. Do not rely on undoing external side effects performed inside normalization.

## Verification

`TemplateMethodChecks.java` covers both normalizations, empty input, fixed operation order, result immutability, null input entries, and omission of the completion hook after validation failure.

```bash
cd examples/template-method
javac --release 21 TemplateMethodDemo.java TemplateMethodChecks.java
java TemplateMethodChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Reuse | Shared order stays consistent while subclasses implement limited variation. |
| Inheritance | Subclass behavior couples to the superclass algorithm and hook contract. |
| Hook growth | Too many hooks make lifecycle reasoning difficult; prefer a smaller strategy-based design when steps vary independently. |

No files are imported; values are supplied in memory. The template validates all items before its completion hook, but subclass operations may still have side effects. The abstraction does not offer rollback if normalization or afterImport performs external work and fails.

## Choosing this pattern

Use this when the sequence is stable and subclasses should vary only a few steps. Keep the hooks narrow and document their timing. If many steps need independent replacement, composition with strategies usually gives more room to change.
