## How it works

A selection rule such as “approved and not obsolete” has a small grammar. A tag tests membership; AND, OR, and NOT combine expressions.

Interpreter represents those expressions as objects. Each node evaluates itself against a set of tags. This example builds the expression tree directly in Java; accepting rule text would require a parser as well.

## Why use it

Hard-coding each rule combination as a new conditional makes a small rule language difficult to compose or inspect. An expression tree makes the grammar explicit and allows rules to be assembled from the same small set of node types.

## Practical use cases

1. Small tag-filter languages for reports or inventories.
2. Simple eligibility expressions over known attributes.
3. Tiny arithmetic or boolean domain languages.
4. Configurable matching rules where a full language engine is unnecessary.

## Java walkthrough

### 1. Write down the grammar

The language has a tag expression and three operators: AND, OR, and NOT. The demo constructs those nodes in Java, so it needs no parser or precedence rules.

### 2. Evaluate a tag

`Tag` checks membership in the supplied set. Names are case-sensitive, and blank names are rejected when the expression is built.

### 3. Combine child expressions

`And` and `Or` use Java’s short-circuit operators. `Not` negates one child. Null children are rejected by the constructors.

### 4. Reuse the rule with different inputs

The same approved-AND-NOT-obsolete tree evaluates two tag sets. The rule is stable; only the context changes.

For example:

```java
Expr rule = new And(new Tag("approved"), new Not(new Tag("obsolete")));
```

### Compile and run

From the repository root:

```bash
cd examples/interpreter
javac --release 21 InterpreterDemo.java
java InterpreterDemo
```

Or run the single-file source directly:

```bash
java InterpreterDemo.java
```

Expected output:

```text
Approved item: true
Obsolete item: false
```

## Extension exercise

Add a text parser for a deliberately small grammar. Define precedence, parentheses, whitespace, invalid-token errors, and maximum nesting before coding it. Keep parsing separate from evaluation, and do not translate untrusted rule text into executable Java.

## Verification

`InterpreterChecks.java` covers aND/OR truth cases, NOT and double negation, contradictory expressions, empty contexts, and malformed node construction.

```bash
cd examples/interpreter
javac --release 21 InterpreterDemo.java InterpreterChecks.java
java InterpreterChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Grammar growth | Each expression form needs another type and tests. |
| Composability | ASTs are easy to assemble but may need a separate parser and error model. |
| Complex languages | A parser library or dedicated engine is often better once typing, binding, or optimization dominates. |

There is no string parser, precedence ambiguity, variable mutation, or external access. The context should remain stable during evaluation. Deep ASTs can exhaust recursion; a production untrusted language needs size and depth limits. This is not a general-purpose rule engine.

## Choosing this pattern

Keep this for a small, well-bounded language. Once parsing, type checking, optimization, or diagnostics becomes the main work, use a language library or rule engine. The expression objects can remain useful even if a parser builds them later.
