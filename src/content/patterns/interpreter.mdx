## The idea in plain English

Interpreter represents a small language as objects that know how to evaluate themselves. A report-selection rule can combine tags with AND, OR, and NOT. Each expression node evaluates its part against a context and combines the results.

> An AST is not a parser: keep the language you actually implement distinct from the language you might later accept as text.

## The problem before the pattern

Hard-coding each rule combination as a new conditional makes a small rule language difficult to compose or inspect. An expression tree makes the grammar explicit and allows rules to be assembled from the same small set of node types.

## Practical use cases

1. Small tag-filter languages for reports or inventories.
2. Simple eligibility expressions over known attributes.
3. Tiny arithmetic or boolean domain languages.
4. Configurable matching rules where a full language engine is unnecessary.

## Java walkthrough

### 1. State the grammar

The grammar has tag, AND, OR, and NOT nodes. This example constructs the AST directly; it has no text parser.

### 2. Implement terminal evaluation

Tag validates its name and tests context membership. Tag matching is exact and case-sensitive.

### 3. Implement composition

And and Or use short-circuit boolean operators. Not negates its child. Constructors reject null operands.

### 4. Evaluate one tree

Build approved AND NOT obsolete, then evaluate it against multiple tag sets without rewriting the rule.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
Expr rule = new And(new Tag("approved"), new Not(new Tag("obsolete")));
```

```bash

```

## Extension exercise

Add a text parser for a deliberately small grammar. Define precedence, parentheses, whitespace, invalid-token errors, and maximum nesting before coding it. Keep parsing separate from evaluation, and do not translate untrusted rule text into executable Java.

## Verification

InterpreterChecks.java verifies: AND/OR truth cases, NOT and double negation, contradictory expressions, empty contexts, and malformed node construction.

```bash
cd examples/interpreter
javac --release 21 InterpreterDemo.java InterpreterChecks.java
java InterpreterChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Grammar growth | Each expression form needs another type and tests. |
| Composability | ASTs are easy to assemble but may need a separate parser and error model. |
| Complex languages | A parser library or dedicated engine is often better once typing, binding, or optimization dominates. |

There is no string parser, precedence ambiguity, variable mutation, or external access. The context should remain stable during evaluation. Deep ASTs can exhaust recursion; a production untrusted language needs size and depth limits. This is not a general-purpose rule engine.
