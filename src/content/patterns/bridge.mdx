## How it works

A detailed report and a summary report answer different questions. Text and HTML are different ways to present either one. These are two separate choices, and combining them in one inheritance tree quickly produces classes such as `DetailedHtmlReport` and `SummaryTextReport`.

Bridge separates those choices. Each report holds a `Renderer`; the report decides what to include, and the renderer supplies the output syntax. Either side can gain a new implementation without adding every possible pairing.

## Why use it

An inheritance-only design might grow DetailedTextReport, DetailedHtmlReport, SummaryTextReport, and SummaryHtmlReport. Adding another report style or output format multiplies combinations. Move rendering operations into a separate interface and let report objects hold a renderer.

## Practical use cases

1. Report detail level versus output format.
2. Engineering views versus drawing backends.
3. Notification urgency versus delivery channel.
4. Device controls versus device-driver implementations.

## Java walkthrough

### 1. Give the renderer a small vocabulary

`Renderer` supplies a heading and an item. It does not decide which items belong in a report. That leaves report composition on the other side of the bridge.

### 2. Pass the renderer to the report

`Report` takes a renderer in its constructor. Before calling `compose`, it checks the title and copies the tool list, so report variants receive the same input guarantees.

### 3. Write the report variants

`DetailedReport` renders every tool. `SummaryReport` renders a count. Both ask their renderer for the pieces they need.

### 4. Combine the two choices

`TextRenderer` and `HtmlRenderer` supply the output syntax. Two report types and two renderers give four combinations without four combined subclasses.

For example:

```java
new SummaryReport(new HtmlRenderer()).render("Tools", tools)
```

## Extension exercise

Add a MarkdownRenderer, then run it with both report classes without modifying them. Separately add an InventoryReport abstraction that groups tools. Verify that it works with the existing renderers. If a new abstraction needs operations missing from Renderer, evolve that interface deliberately rather than downcasting.

## Verification

`BridgeChecks.java` covers all four report/renderer combinations, empty summaries, HTML text escaping, rejection of null dependencies, and preservation of report input.

```bash
cd examples/bridge
javac --release 21 BridgeDemo.java BridgeChecks.java
java BridgeChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Two dimensions of change | Composition avoids a class for every pair, at the cost of an extra abstraction. |
| Implementor interface | Keep operations useful to all report variants; overly specialized primitives create coupling. |
| Changing implementors | This example fixes its renderer at construction; runtime replacement is a separate policy. |

The example renders fragments, not complete HTML documents. HTML escaping handles text nodes only. It assumes single-line text for the plain renderer. Renderers are stateless here; a stateful drawing backend would need explicit ownership and concurrency rules.

## Choosing this pattern

Look for two real sources of variation. Here, report detail and output format can change independently. If only the renderer varies, a single injected interface may be enough; a second hierarchy would add little.
