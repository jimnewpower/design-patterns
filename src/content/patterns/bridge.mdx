## The idea in plain English

Bridge separates a high-level abstraction from the implementation it delegates to, so both can change independently. A report can be detailed or summarized, while its rendering can be text or HTML. You can combine either report with either renderer without creating a subclass for every pair.

> Two interfaces alone are not enough: identify the two independent axes and verify useful combinations along both.

## The problem before the pattern

An inheritance-only design might grow DetailedTextReport, DetailedHtmlReport, SummaryTextReport, and SummaryHtmlReport. Adding another report style or output format multiplies combinations. Move rendering operations into a separate interface and let report objects hold a renderer.

## Practical use cases

1. Report detail level versus output format.
2. Engineering views versus drawing backends.
3. Notification urgency versus delivery channel.
4. Device controls versus device-driver implementations.

## Java walkthrough

### 1. Define implementation primitives

Renderer exposes heading and item operations rather than the whole report algorithm. This keeps composition decisions in the abstraction.

### 2. Compose through the bridge

Report validates input and passes a defensive list snapshot to compose. Its constructor accepts the renderer, making the relationship explicit.

### 3. Vary the abstraction

DetailedReport iterates through tools; SummaryReport emits a count. Neither selects HTML or text classes.

### 4. Vary the implementation

TextRenderer and HtmlRenderer implement the same primitives. Startup combines a report and a renderer; four combinations require only two classes on each side.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
new SummaryReport(new HtmlRenderer()).render("Tools", tools)
```


## Extension exercise

Add a MarkdownRenderer, then run it with both report classes without modifying them. Separately add an InventoryReport abstraction that groups tools. Verify that it works with the existing renderers. If a new abstraction needs operations missing from Renderer, evolve that interface deliberately rather than downcasting.

## Verification

BridgeChecks.java verifies: All four report/renderer combinations, empty summaries, HTML text escaping, rejection of null dependencies, and preservation of report input.

```bash
cd examples/bridge
javac --release 21 BridgeDemo.java BridgeChecks.java
java BridgeChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Two dimensions of change | Composition avoids a class for every pair, at the cost of an extra abstraction. |
| Implementor interface | Keep operations useful to all report variants; overly specialized primitives create coupling. |
| Changing implementors | This example fixes its renderer at construction; runtime replacement is a separate policy. |

The example renders fragments, not complete HTML documents. HTML escaping handles text nodes only. It assumes single-line text for the plain renderer. Renderers are stateless here; a stateful drawing backend would need explicit ownership and concurrency rules.
