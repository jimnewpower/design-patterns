## How it works

Start with a report body, wrap it in a header, then wrap that in a footer. The result still behaves like a report: callers use `render()` without needing to know which wrappers are present.

That is Decorator. Each wrapper adds one piece of behavior and delegates the rest. It is useful when features need to combine without a subclass for every combination.

## Why use it

Subclassing for every combination of headers, footers, formatting, and other features causes a proliferation of report types. A boolean-heavy report class concentrates unrelated options. Independent wrappers let each feature compose around the existing object.

## Practical use cases

1. Headers, footers, and formatting around reports.
2. Buffered or filtered I/O streams.
3. Metrics and tracing around a service contract.
4. Optional transformations in rendering pipelines.

## Java walkthrough

### 1. Start with the component contract

`Report` has one method, `render()`. A plain report and every decorator implement it, so a wrapper can hold either kind of object.

### 2. Store the object being wrapped

`ReportDecorator` keeps a non-null `Report` reference. It deliberately does not require a `PlainReport`; that would prevent stacking decorators.

### 3. Add a header or footer

`Header` prepends its title, and `Footer` appends its note. Each delegates to the wrapped report once. The original body is unchanged.

### 4. Build the wrapper chain

The demo constructs a footer around a header around a plain body. Reading that construction shows which features are present.

For example:

```java
return title + "\n" + wrapped.render();
```

## Verification

`DecoratorChecks.java` covers composed rendering, repeated headers and footers, wrapper ordering, preservation of the original body, and null dependencies.

```bash
cd examples/decorator
javac --release 21 DecoratorDemo.java DecoratorChecks.java
java DecoratorChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Runtime composition | Features combine flexibly but a long wrapper chain can be difficult to inspect. |
| Same interface | Preserve the component contract, including errors and lifecycle behavior. |
| Ordering | Treat wrapper order as behavior and verify it rather than assuming every order is equivalent. |

Text is rendered synchronously with no escaping or layout engine. Header and footer happen to commute with each other in this small example; decorators in general do not. Wrapping resource-owning services also requires explicit close and error semantics.

## Related patterns

| Approach | Distinction |
| --- | --- |
| Adapter | Changes the expected interface or semantics; Decorator preserves the component contract while adding behavior. |
| Proxy | Controls access or lifecycle; Decorator primarily augments behavior. |

## Choosing this pattern

This is a good fit for features that need to combine independently around one stable contract. Keep the wrappers small. As chains grow, give their construction a readable home and test the order-sensitive combinations.
