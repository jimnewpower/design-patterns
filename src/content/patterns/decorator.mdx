## The idea in plain English

Decorator adds behavior by wrapping an object behind the same interface. A basic report renders its body. A header decorator prepends a title, while a footer decorator appends a note. Clients can combine these at runtime and still use Report.

> A wrapper is not automatically a Decorator: identify the preserved interface and the added responsibility.

## The problem before the pattern

Subclassing for every combination of headers, footers, formatting, and other features causes a proliferation of report types. A boolean-heavy report class concentrates unrelated options. Independent wrappers let each feature compose around the existing object.

## Practical use cases

1. Headers, footers, and formatting around reports.
2. Buffered or filtered I/O streams.
3. Metrics and tracing around a service contract.
4. Optional transformations in rendering pipelines.

## Java walkthrough

### 1. Keep one component contract

Report exposes render. Both core objects and decorators satisfy it.

### 2. Store a wrapped component

ReportDecorator validates and stores its delegate. It does not demand a PlainReport, so decorators can wrap other decorators.

### 3. Add one responsibility

Header prepends its title; Footer appends its note. Each calls wrapped.render exactly once.

### 4. Compose at startup

Build Footer(Header(PlainReport)) to choose the desired features without another combined subclass.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
return title + "\n" + wrapped.render();
```

## Verification

DecoratorChecks.java verifies: Composed rendering, repeated headers and footers, wrapper ordering, preservation of the original body, and null dependencies.

```bash
cd examples/decorator
javac --release 21 DecoratorDemo.java DecoratorChecks.java
java DecoratorChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Runtime composition | Features combine flexibly but a long wrapper chain can be difficult to inspect. |
| Same interface | Preserve the component contract, including errors and lifecycle behavior. |
| Ordering | Treat wrapper order as behavior and verify it rather than assuming every order is equivalent. |

Text is rendered synchronously with no escaping or layout engine. Header and footer happen to commute with each other in this small example; decorators in general do not. Wrapping resource-owning services also requires explicit close and error semantics.

## Compare related patterns

| Approach | Distinction |
| --- | --- |
| Adapter | Changes the expected interface or semantics; Decorator preserves the component contract while adding behavior. |
| Proxy | Controls access or lifecycle; Decorator primarily augments behavior. |
