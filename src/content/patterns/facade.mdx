## How it works

Publishing a release involves several calls: validate its content, store it, then notify interested users. If every caller repeats those steps, their order and error handling tend to drift.

`ReleaseFacade.publish()` gives callers one operation for that workflow. Validation, storage, and notification still live in separate collaborators; the facade coordinates them.

## Why use it

If each caller repeats the same subsystem calls, order and failure behavior drift. Some callers may notify before storage succeeds. A facade makes the supported workflow explicit while leaving specialized subsystem APIs available where appropriate.

## Practical use cases

1. Publishing an engineering release across validation and archive services.
2. A simplified checkout flow over inventory, payment, and shipping APIs.
3. A reporting entry point over query, formatting, and storage modules.
4. A legacy subsystem entry point during incremental modernization.

## Java walkthrough

### 1. Keep subsystem responsibilities separate

The validator, archive, and notifier have separate interfaces. Tests can record their calls or make one fail without changing the facade.

### 2. Validate before storing

`publish()` rejects a null release, then asks the validator to check it. A validation failure stops the workflow before archive or notification calls occur.

### 3. Pass the stored identifier to notification

The archive returns an identifier. The facade checks that it is non-null and gives that same identifier to the notifier.

### 4. Give callers one operation

The caller supplies a release and receives its identifier. If a step throws, the exception reaches the caller; successful earlier side effects remain.

For example:

```java
String id = Objects.requireNonNull(archive.store(release));
notifier.notifyRelease(id);
```


## Extension exercise

Introduce a notification failure and decide how production should recover. An outbox or retryable delivery record can preserve intent after storage. Do not claim a facade makes independent services atomic. Add an idempotency key only after defining duplicate-publish semantics.

## Verification

`FacadeChecks.java` covers call order and identifier propagation, validation failure before side effects, archive failure suppressing notification, and notification failure leaving the archive action completed.

```bash
cd examples/facade
javac --release 21 FacadeDemo.java FacadeChecks.java
java FacadeChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Convenience | A focused workflow reduces caller complexity, but an all-purpose facade can become a large service. |
| Error semantics | Document partial success and preserve meaningful failures. |
| Subsystem access | A facade is a convenience boundary, not automatically an authorization or encapsulation barrier. |

The example uses in-memory callbacks and does not send notifications. It has no transaction, rollback, persistence, retries, or distributed coordination. A notifier failure can occur after archive success; the caller receives the failure but must not assume nothing happened.

## Related patterns

| Approach | Distinction |
| --- | --- |
| Adapter | Implements a client-required contract for an incompatible component; Facade offers a simpler subsystem entry point. |
| Mediator | Coordinates peer interactions; a Facade usually orchestrates a request into subsystems. |

## Choosing this pattern

A facade helps when callers repeatedly perform the same subsystem workflow. Keep that workflow focused and be clear about partial success. If notification fails after archiving, the archive still exists; the shorter API does not make the operation transactional.
