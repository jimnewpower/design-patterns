## The idea in plain English

An Abstract Factory supplies a **family of related objects**. The code using those objects knows their interfaces, while the chosen factory determines their concrete implementations.

Imagine a report with a heading and a table. An HTML report needs an HTML heading and an HTML table. A plain-text report needs both text equivalents. Choose the family once, then let its factory create the members.

> Use it when you have multiple product types and interchangeable families that should stay compatible.

## The problem before the pattern

Without a factory, a report generator might choose every component itself:

```java
if ("html".equals(format)) {
    heading = new HtmlHeadingRenderer();
    table = new HtmlTableRenderer();
} else {
    heading = new TextHeadingRenderer();
    table = new TextTableRenderer();
}
```

The generator now knows concrete classes and format-selection rules. Repeated selection logic can drift, leaving one part HTML and another plain text. Abstract Factory moves that responsibility into a dedicated collaborator, selected near application startup.

For this small example, injecting the two renderers directly would also be reasonable. The factory earns its place as creating a matching family becomes a recurring concern.

## Practical use cases

1. **UI toolkits:** supply matching buttons, menus, and dialogs for an operating system or theme.
2. **Report generation:** supply headings, tables, and footers for HTML, text, or Markdown.
3. **Database adapters:** supply a vendor’s SQL dialect, schema inspector, and bulk loader.
4. **Cloud adapters:** supply storage, messaging, and secrets components for a selected provider.

In each case, there are several product roles and a coherent set of implementations for each family.

## Structure and pattern roles

| GoF role | Java types | Responsibility |
| --- | --- | --- |
| Abstract Factory | `ReportComponentFactory` | Declare product-creation operations. |
| Concrete Factory | `HtmlReportFactory`, `TextReportFactory` | Supply one matching family. |
| Abstract Product | `HeadingRenderer`, `TableRenderer` | Define the capabilities the client uses. |
| Concrete Product | HTML and text implementations of both renderers | Implement format-specific behavior. |
| Client | `ReportGenerator` | Assemble a report through product interfaces. |

“Abstract” here means expressed through an abstraction; a Java interface works well. It does not require a Java abstract class.

## Java walkthrough

### 1. Define the product interfaces

```java
interface HeadingRenderer {
    String render(String title);
}
interface TableRenderer {
    String render(String columnName, List<String> values);
}
```

The generator needs these capabilities without knowing which format implements them. All snippets use `java.util.List` where needed; the complete listing includes its import.

### 2. Implement each product family

The HTML heading renders an escaped title inside an `h1`. The text heading adds a simple underline. Each family also provides a table renderer.

```java
static final class HtmlHeadingRenderer implements HeadingRenderer {
    public String render(String title) {
        return "<h1>" + Html.escape(title) + "</h1>";
    }
}
static final class TextHeadingRenderer implements HeadingRenderer {
    public String render(String title) {
        return title + "\n" + "=".repeat(title.length());
    }
}
```

`Html.escape` handles text-node content (`&`, `<`, `>`). It is not an attribute escaper or a general-purpose HTML sanitizer. This example assumes non-null strings and collections.

### 3. Declare the factory interface

```java
interface ReportComponentFactory {
    HeadingRenderer createHeadingRenderer();
    TableRenderer createTableRenderer();
}
```

One creation method per product type makes the family visible. The return types are product interfaces.

### 4. Create a factory for each family

```java
static final class HtmlReportFactory implements ReportComponentFactory {
    public HeadingRenderer createHeadingRenderer() {
        return new HtmlHeadingRenderer();
    }
    public TableRenderer createTableRenderer() {
        return new HtmlTableRenderer();
    }
}
```

`TextReportFactory` follows the same structure and returns text products. Concrete factories own knowledge of concrete classes.

### 5. Inject the factory into the client

```java
ReportGenerator(ReportComponentFactory factory) {
    heading = factory.createHeadingRenderer();
    table = factory.createTableRenderer();
}
```

`ReportGenerator` stores the product interfaces and delegates rendering to them. It has no HTML/text conditional and no concrete-product constructor calls.

### 6. Choose the family at startup

```java
ReportComponentFactory factory = new HtmlReportFactory();
ReportGenerator generator = new ReportGenerator(factory);
```

Use `TextReportFactory` to change the family. Configuration and dependency injection can make this selection at the application’s composition root. DI and Abstract Factory work together: DI supplies the factory; the factory creates related products.

## Extend it: add Markdown

Add two product implementations and a factory. The report generator stays unchanged.

```java
static final class MarkdownHeadingRenderer implements HeadingRenderer {
    public String render(String title) {
        return "# " + title;
    }
}
static final class MarkdownTableRenderer implements TableRenderer {
    public String render(String columnName, List<String> values) {
        StringBuilder output = new StringBuilder(columnName);
        for (String value : values) output.append("\n- ").append(value);
        return output.toString();
    }
}
static final class MarkdownReportFactory implements ReportComponentFactory {
    public HeadingRenderer createHeadingRenderer() {
        return new MarkdownHeadingRenderer();
    }
    public TableRenderer createTableRenderer() {
        return new MarkdownTableRenderer();
    }
}
```

Place these classes inside `AbstractFactoryDemo`, then add a `markdown` case to the startup switch. This teaching extension uses a Markdown heading and a list for the single-column table; it assumes trusted, single-line text. Production Markdown rendering needs deliberate escaping and formatting rules.

**Exercise:** add a footer product next. Which interfaces and factories must change? All factories now need a footer creation method, even though adding the Markdown family did not change the factory interface.

## Verification

The repository includes dependency-free behavior checks in `AbstractFactoryChecks.java`:

- Exact plain-text and HTML output from the client.
- HTML escaping in headings, column names, and values.
- Empty-table behavior.
- Rejection of an unsupported output format.

Run them with Java 21:

```bash
cd examples/abstract-factory
javac --release 21 AbstractFactoryDemo.java AbstractFactoryChecks.java
java AbstractFactoryChecks
```

A failure throws `AssertionError`; no `-ea` flag is required. CI runs these checks independently of the site build. The tests verify observable behavior rather than the private construction details.

## Tradeoffs and common mistakes

| Change | Effect |
| --- | --- |
| Add a new family | Implement the existing products and add a concrete factory. Update startup selection. |
| Change HTML rendering | Modify the relevant HTML product implementation. |
| Add a new product type | Change the factory interface and every concrete factory. |
| Replace the active family | Supply another factory to a new client instance. |

**Compatibility is a design promise.** These interfaces permit a badly implemented factory to return an HTML heading and a text table. The example’s factories keep families consistent by convention; the type system does not enforce a family identifier.

Avoid these mistakes:

- Introducing a factory for one simple interchangeable object when direct injection is sufficient.
- Calling concrete-product constructors inside the client.
- Scattering family selection across business logic.
- Assuming a factory must create fresh instances every time. Reuse is a lifecycle decision, provided the product contract permits it.
- Treating the pattern as proof that products are thread-safe or compatible. Those properties require their own contracts and verification.

## Compare related approaches

| Approach | Central concern | Compared with Abstract Factory |
| --- | --- | --- |
| Factory Method | A creation hook that subclasses override | Uses inheritance to vary creation; Abstract Factory usually supplies a family through composition. A concrete factory can itself use factory methods. |
| Builder | Stepwise construction of a complex result | Organizes construction steps rather than choosing a family of collaborators. |
| Strategy | Interchangeable behavior or algorithms | Replaces a behavior; Abstract Factory creates related objects. |
| Constructor injection | Explicitly supply dependencies | Often simpler for a few collaborators. A factory can itself be injected when family creation belongs together. |

## Quick reference

- **Intent:** create related products through interfaces.
- **Recognize it:** several product roles, several matching families.
- **Choose:** the concrete factory at startup.
- **Keep stable:** the client and product interfaces when adding families.
- **Expect friction:** when adding a new product role.
- **Ask first:** would directly injecting the products be simpler?
