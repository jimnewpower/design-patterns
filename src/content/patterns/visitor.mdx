## How it works

A parts tree may need several operations: total its mass, print an outline, calculate a cost, or check a rule. Putting all of them on every element can make the model cumbersome.

Visitor groups the code for each operation in a separate class. Parts and assemblies accept a visitor and dispatch to its type-specific method. This works best when the element types are fairly stable and the list of operations keeps growing.

## Why use it

A stable part tree may need mass, cost, export, and validation operations. Adding every operation directly to each element bloats the model. A visitor keeps one operation together across element types, provided those types are relatively stable.

## Practical use cases

1. Multiple analyses over a stable engineering model.
2. AST printing, checking, or code generation.
3. Exports of a fixed document element hierarchy.
4. Aggregation over stable leaf/composite structures.

## Java walkthrough

### 1. Keep the element types small

`Part` and `Assembly` hold the model data and implement `Item`. They do not contain mass or outline algorithms.

### 2. Dispatch to the element-specific method

A part calls `visitor.visitPart(this)`; an assembly calls `visitAssembly(this)`. The element and visitor together select the method body.

### 3. Implement an operation in one visitor

`MassVisitor` returns a leaf’s stored grams and totals a group with `Math.addExact`. Its two methods belong together because they implement one analysis.

### 4. Let the visitor choose traversal

The assembly visit recurses into children. `OutlineVisitor` formats those results, while a test-only visitor counts leaves without changing the elements.

For example:

```java
public <R> R accept(Visitor<R> visitor) { return visitor.visitPart(this); }
```

## Extension exercise

Add a CostVisitor using a supplied part-price map and explicit missing-price errors. Then add a new element type and observe that every visitor must implement its method. That contrast is the pattern’s central tradeoff, not a defect to hide with default empty implementations.

## Verification

`VisitorChecks.java` covers leaf and nested aggregates, outline traversal order, empty assemblies, a new count operation, invalid mass/input, and arithmetic overflow.

```bash
cd examples/visitor
javac --release 21 VisitorDemo.java VisitorChecks.java
java VisitorChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| New operations | Add a visitor without editing the existing elements. |
| New element types | Change the visitor interface and update every operation. |
| Encapsulation | Visitors need enough element data to work; avoid exposing unrelated mutable internals. |

The model is an immutable tree with integral grams. Visitors perform recursive traversal, so deep or cyclic graphs need another policy. Visitor methods intentionally know concrete element types. This is not a general traversal API for unknown types loaded at runtime.

## Related patterns

| Approach | Distinction |
| --- | --- |
| Composite | Models the tree; Visitor adds operations over its element types. |
| Iterator | Exposes traversal to a caller; Visitor dispatches by element type and can own recursion. |

## Choosing this pattern

Visitor makes adding an operation cheap and adding an element type expensive. Choose it when that matches the model’s direction of change. Keep traversal ownership clear so a visitor does not accidentally process children twice or skip them.
