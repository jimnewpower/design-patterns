## The idea in plain English

Visitor adds operations to a stable object structure by dispatching an operation to the concrete element type. Parts and assemblies accept a visitor; a mass visitor totals grams while an outline visitor prints names. The element classes do not contain those operations.

> Use Visitor when operations change more frequently than element types, and state who owns traversal.

## The problem before the pattern

A stable part tree may need mass, cost, export, and validation operations. Adding every operation directly to each element bloats the model. A visitor keeps one operation together across element types, provided those types are relatively stable.

## Practical use cases

1. Multiple analyses over a stable engineering model.
2. AST printing, checking, or code generation.
3. Exports of a fixed document element hierarchy.
4. Aggregation over stable leaf/composite structures.

## Java walkthrough

### 1. Keep element structure stable

Part and Assembly are immutable records behind a sealed Item interface.

### 2. Perform double dispatch

accept calls visitPart(this) or visitAssembly(this). Runtime element dispatch chooses the accept body; visitor dispatch chooses the operation implementation.

### 3. Put an operation together

MassVisitor handles leaves and groups in one class, using exact addition to reject overflow.

### 4. Choose traversal ownership

Visitors recurse into assembly children themselves. OutlineVisitor selects its own formatting, and a test-only count visitor adds an operation without changing elements.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
public <R> R accept(Visitor<R> visitor) { return visitor.visitPart(this); }
```

## Extension exercise

Add a CostVisitor using a supplied part-price map and explicit missing-price errors. Then add a new element type and observe that every visitor must implement its method. That contrast is the pattern’s central tradeoff, not a defect to hide with default empty implementations.

## Verification

VisitorChecks.java verifies: Leaf and nested aggregates, outline traversal order, empty assemblies, a new count operation, invalid mass/input, and arithmetic overflow.

```bash
cd examples/visitor
javac --release 21 VisitorDemo.java VisitorChecks.java
java VisitorChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| New operations | Add a visitor without editing the existing elements. |
| New element types | Change the visitor interface and update every operation. |
| Encapsulation | Visitors need enough element data to work; avoid exposing unrelated mutable internals. |

The model is an immutable tree with integral grams. Visitors perform recursive traversal, so deep or cyclic graphs need another policy. Visitor methods intentionally know concrete element types. This is not a general traversal API for unknown types loaded at runtime.

## Compare related patterns

| Approach | Distinction |
| --- | --- |
| Composite | Models the tree; Visitor adds operations over its element types. |
| Iterator | Exposes traversal to a caller; Visitor dispatches by element type and can own recursion. |
