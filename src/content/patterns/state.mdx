## The idea in plain English

State delegates behavior to an object representing the context’s current state. A review workflow accepts different actions while Draft, Review, or Approved. Each state object defines the actions and transitions valid at that point.

> Do not replace a clear three-state switch with classes automatically; the pattern earns its place when state-dependent behavior becomes substantial.

## The problem before the pattern

Repeated switches over a status field scatter transition rules across submit, approve, and reopen operations. A new state then requires coordinated edits to many conditionals. State objects group behavior by the state that owns it.

## Practical use cases

1. Review and approval workflows.
2. Connection or protocol lifecycle handling.
3. Order fulfillment transitions.
4. UI controls whose behavior depends on a mode.

## Java walkthrough

### 1. Define state-dependent actions

ReviewState declares submit, approve, and reopen. Default implementations throw without changing the context.

### 2. Implement allowed transitions

Draft submits to Review. Review approves to Approved or reopens to Draft. Approved reopens to Draft.

### 3. Keep state ownership local

Each Workflow stores its own current reference. Stateless enum state objects can be shared across contexts without sharing the contexts’ current states.

### 4. Delegate instead of switch

Workflow forwards actions and asks state.label for status. Transition logic stays in the concrete state objects.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
void submit() { state.submit(this); }
void approve() { state.approve(this); }
```

## Extension exercise

Add a Rejected state and a reject action. Decide which states can reopen and which reject actions are invalid. Write a transition table first, then test every permitted edge and representative forbidden edges. Add audit records without exposing a public arbitrary setState operation.

## Verification

StateChecks.java verifies: Full approval path, reopening from Review and Approved, forbidden operations preserving state, and independent workflow contexts.

```bash
cd examples/state
javac --release 21 StateDemo.java StateChecks.java
java StateChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Local behavior | Rules for one state stay together, but small state machines may be clearer as a transition table. |
| Transitions | Concrete states know neighboring states, which is intentional coupling. |
| Persistence | Persist stable domain state identifiers and restore deliberately rather than serializing implementation objects blindly. |

This is a synchronous in-memory state machine with no actor permissions, persistence, or transaction boundary. Concurrent actions need serialization or another concurrency model. Shared state objects must remain stateless; request-specific mutable data belongs to the context.
