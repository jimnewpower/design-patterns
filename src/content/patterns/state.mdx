## How it works

Submitting a draft should send it for review. Submitting an already approved report should fail. The same operation has different behavior depending on where the report is in its lifecycle.

State puts that behavior in objects representing Draft, Review, and Approved. The workflow delegates an action to its current state; that state either performs a transition or rejects the action.

## Why use it

Repeated switches over a status field scatter transition rules across submit, approve, and reopen operations. A new state then requires coordinated edits to many conditionals. State objects group behavior by the state that owns it.

## Practical use cases

1. Review and approval workflows.
2. Connection or protocol lifecycle handling.
3. Order fulfillment transitions.
4. UI controls whose behavior depends on a mode.

## Java walkthrough

### 1. Define the lifecycle actions

`ReviewState` declares submit, approve, and reopen. An action fails by default; each state overrides only the actions it accepts.

### 2. Put transitions with their states

Draft submits to Review. Review can approve or reopen. Approved can reopen. Those rules live in the corresponding state types.

### 3. Keep the current state on the workflow

Each `Workflow` holds its own state reference. The enum instances carry no per-workflow data, so several workflows can safely use the same state objects.

### 4. Delegate each action

`Workflow.submit()` calls `state.submit(this)`. Status comes from `state.label()`. The context needs no switch over the lifecycle.

For example:

```java
void submit() { state.submit(this); }
void approve() { state.approve(this); }
```

## Extension exercise

Add a Rejected state and a reject action. Decide which states can reopen and which reject actions are invalid. Write a transition table first, then test every permitted edge and representative forbidden edges. Add audit records without exposing a public arbitrary setState operation.

## Verification

`StateChecks.java` covers full approval path, reopening from Review and Approved, forbidden operations preserving state, and independent workflow contexts.

```bash
cd examples/state
javac --release 21 StateDemo.java StateChecks.java
java StateChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Local behavior | Rules for one state stay together, but small state machines may be clearer as a transition table. |
| Transitions | Concrete states know neighboring states, which is intentional coupling. |
| Persistence | Persist stable domain state identifiers and restore deliberately rather than serializing implementation objects blindly. |

This is a synchronous in-memory state machine with no actor permissions, persistence, or transaction boundary. Concurrent actions need serialization or another concurrency model. Shared state objects must remain stateless; request-specific mutable data belongs to the context.

## Choosing this pattern

Group behavior by state when submit, approve, reopen, and similar operations are each accumulating status checks. A small transition table can be clearer for a simple lifecycle. State objects help when each state has enough behavior to justify a type.
