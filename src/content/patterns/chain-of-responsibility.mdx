## How it works

A team lead can approve a small purchase. A larger one goes to a manager. If neither has enough authority, the request is rejected.

Chain of Responsibility represents that escalation as linked handlers. A handler either answers the request or passes it on. The caller submits to the first handler and does not need to choose the eventual approver.

## Why use it

A central approval function can accumulate role-specific conditionals and escalation rules. Callers should submit a request without knowing which approver will accept it. Linked handlers keep each decision local and make ordering explicit at construction.

## Practical use cases

1. Approval escalation by authority or amount.
2. Request handlers that try progressively broader matches.
3. Help systems that search parent contexts for an answer.
4. Validation or processing stages with explicit continuation policy.

## Java walkthrough

### 1. Represent the request

`Request` holds a purpose and a nonnegative cost. These are abstract cost units; the example does not attempt currency conversion or authorization.

### 2. Decide whether to handle or pass on

A `LimitApprover` compares the cost with its limit. It approves requests at or below the limit and passes larger ones to its successor.

### 3. Assemble the escalation order

The client links a team lead to a manager. Each handler knows only its own decision and the next handler, not the entire approval policy.

### 4. Finish with a rejection handler

`Reject` gives uncovered requests an explicit outcome. The caller receives a decision string even when nobody can approve.

For example:

```java
return request.cost() <= limit ? "Approved by " + name : next.handle(request);
```

From the repository root:

```bash
cd examples/chain-of-responsibility
javac --release 21 ChainOfResponsibilityDemo.java
java ChainOfResponsibilityDemo
```

```bash
java ChainOfResponsibilityDemo.java
```

Expected output:

```text
Approved by Team lead
Approved by Manager
Rejected: no approval limit covers request
```

Add an AuditHandler that records decisions. Decide whether it wraps the whole chain or only logs requests that reach it. Tests should prove whether approved requests continue or stop. Also test reordered limits so an overly broad first handler does not silently bypass intended review.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Ordering | The first capable handler wins; changing order changes behavior. |
| Unhandled requests | Define an explicit rejection or fallback rather than dropping requests. |
| Topology | Mutable successor graphs need cycle prevention; an immutable constructed chain simplifies ownership. |

The chain is assembled as immutable forward references and has no remote calls or identity-based authorization. Name and limit are teaching configuration, not proof of authority. This first-match example is different from a pipeline where every stage must process the request.

## Related patterns

| Approach | Distinction |
| --- | --- |

## Choosing this pattern

Use a chain when the handler is determined as the request moves through it. Make ordering and termination obvious. A first-match approval chain and a pipeline that runs every stage may look similar in code, but callers need very different guarantees.
