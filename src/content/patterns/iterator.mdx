## The idea in plain English

Iterator separates traversal state from the collection it traverses. Each caller receives its own cursor, asks whether another value exists, and requests the next value without seeing the collection representation.

> The edge cases are the contract: independent cursors, exhaustion, mutation, and resource lifetime matter as much as the happy-path loop.

## The problem before the pattern

Exposing indexes and internal lists forces clients to know how a catalog is stored. Keeping a single cursor on the catalog also causes independent callers to interfere. Returning a new iterator per traversal isolates that state.

## Practical use cases

1. Iterating a custom collection through Java enhanced-for syntax.
2. Traversing trees or graphs with a chosen ordering.
3. Reading a sequence whose storage representation may change.
4. Paged data access with explicit lifecycle and fetch semantics.

## Java walkthrough

### 1. Snapshot collection input

ToolCatalog copies its tool list and rejects null data through List.copyOf.

### 2. Create a new cursor

iterator returns a fresh anonymous object each time. Its index belongs to that object.

### 3. Honor hasNext and next

hasNext never advances. next checks exhaustion and throws NoSuchElementException instead of returning a sentinel.

### 4. Use standard traversal

Iterable integrates with enhanced-for and forEach. remove inherits the unsupported-operation default.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
if (!hasNext()) throw new NoSuchElementException("End of catalog");
return tools.get(index++);
```

## Extension exercise

Implement depth-first traversal for an assembly tree using an explicit stack. Define whether groups are emitted, whether repeated placements are repeated, and how cycles are handled for graph input. For remote paging, add explicit close/cancellation instead of hiding resource ownership behind a plain iterator.

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Encapsulation | Storage stays hidden, but traversal order remains part of the public contract. |
| Cursor state | Each traversal needs its own mutable object. |
| Mutation | Document snapshot, fail-fast, or weakly consistent semantics when the source can change. |

The catalog is immutable and in memory. Each iterator is mutable and not thread-safe. Immutability removes collection-modification ambiguity in this example; it is not an example of a fail-fast mutable iterator. Java iterators do not automatically close external resources.
