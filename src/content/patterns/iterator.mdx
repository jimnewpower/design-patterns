## How it works

Two callers should be able to walk the same catalog without moving each other’s cursor. They also should not need access to the catalog’s internal list or indexes.

An iterator holds the traversal position separately from the collection. Each call to `iterator()` returns a new cursor with `hasNext()` and `next()`. Implementing Java’s `Iterable` interface also lets the catalog work in an enhanced-for loop.

## Why use it

Exposing indexes and internal lists forces clients to know how a catalog is stored. Keeping a single cursor on the catalog also causes independent callers to interfere. Returning a new iterator per traversal isolates that state.

## Practical use cases

1. Iterating a custom collection through Java enhanced-for syntax.
2. Traversing trees or graphs with a chosen ordering.
3. Reading a sequence whose storage representation may change.
4. Paged data access with explicit lifecycle and fetch semantics.

## Java walkthrough

### 1. Take ownership of the collection values

`ToolCatalog` copies the supplied list. Later changes to that list cannot change an existing catalog.

### 2. Give each traversal its own index

Every call to `iterator()` creates a new anonymous iterator with its own `index` field. Interleaved callers therefore advance independently.

### 3. Handle the end correctly

`hasNext()` only checks availability. `next()` advances after returning a value and throws `NoSuchElementException` once exhausted.

### 4. Use Java’s traversal syntax

Implementing `Iterable` makes enhanced-for and `forEach` work. The iterator keeps the default unsupported `remove()` operation.

For example:

```java
if (!hasNext()) throw new NoSuchElementException("End of catalog");
return tools.get(index++);
```

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Encapsulation | Storage stays hidden, but traversal order remains part of the public contract. |
| Cursor state | Each traversal needs its own mutable object. |
| Mutation | Document snapshot, fail-fast, or weakly consistent semantics when the source can change. |

The catalog is immutable and in memory. Each iterator is mutable and not thread-safe. Immutability removes collection-modification ambiguity in this example; it is not an example of a fail-fast mutable iterator. Java iterators do not automatically close external resources.

## Choosing this pattern

Use the standard Iterator and Iterable contracts when possible. Most of the work is in the edges: exhaustion, independent cursors, source mutation, and resource lifetime. A remote cursor that owns a connection needs more than a next method.
