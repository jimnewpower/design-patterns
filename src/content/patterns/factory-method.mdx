## How it works

The export workflow is the same for text and HTML: validate the input, obtain a formatter, then format the report. Only the formatter changes.

Factory Method puts a creation hook in that shared workflow. `ReportExport.export()` calls `createFormatter()`, and a subclass supplies the formatter. The subclass inherits the workflow instead of copying it.

## Why use it

A workflow might directly construct its formatter:

```java
String export(String title, List<String> tools) {
    // Validate inputs...
    ReportFormatter formatter = new HtmlReportFormatter();
    return formatter.format(title, tools);
}
```

Now the workflow is tied to HTML. Copying it for text duplicates its validation and orchestration. Adding format conditionals inside it mixes selection with the workflow.

Replace the constructor call with `createFormatter()`. Each subclass implements that hook and inherits `export()`. Startup still chooses the exporter; the shared workflow no longer needs to make that choice.

## Practical use cases

1. **Report export frameworks:** subclasses supply a formatter while inheriting validation and report processing.
2. **Document applications:** a base application handles document workflows while subclasses create different document implementations.
3. **UI frameworks:** a dialog workflow obtains a platform-specific control through an overridable creation method.
4. **Import pipelines:** a base importer coordinates processing while subclasses supply a parser for a supported source format.

In every case, the creator has useful behavior beyond object construction. If it only wraps a constructor, direct dependency injection or a simple factory may express the design more clearly.

The **factory method** is `createFormatter()`. `export()` is the business operation that calls it. The abstract creator need not be a standalone factory service.

## Java walkthrough

### 1. Define the product interface

```java
interface ReportFormatter {
    String format(String title, List<String> tools);
}
```

The creator can use any product satisfying this contract. Its workflow does not need concrete formatter names.

### 2. Define the creator and its hook

```java
abstract static class ReportExport {
    public final String export(String title, List<String> tools) {
        Objects.requireNonNull(title, "title");
        if (title.isBlank()) throw new IllegalArgumentException("Title must not be blank");
        List<String> snapshot = List.copyOf(tools);
        ReportFormatter formatter = Objects.requireNonNull(createFormatter(), "formatter");
        return formatter.format(title, snapshot);
    }
    protected abstract ReportFormatter createFormatter();
}
```

`export` validates the title and takes an unmodifiable snapshot of the tool list before selecting the formatter. Null lists and null elements are rejected. Strings are immutable, so no element-level copying is needed here.

Here, `export()` is final so subclasses extend only the creation step. The protected hook keeps formatter construction behind the public workflow. Other implementations can choose different visibility and extension rules.

Do not call an overridable factory method from the superclass constructor: subclass initialization may not have completed yet.

### 3. Supply concrete creators

```java
static final class HtmlReportExport extends ReportExport {
    @Override
    protected ReportFormatter createFormatter() {
        return new HtmlReportFormatter();
    }
}
```

`TextReportExport` returns `TextReportFormatter` in the same way. These subclasses inherit `export`; they do not duplicate or replace the workflow.

### 4. Implement the products

```java
static final class TextReportFormatter implements ReportFormatter {
    @Override
    public String format(String title, List<String> tools) {
        StringBuilder output = new StringBuilder(title)
                .append("\n").append("=".repeat(title.length())).append("\n\nTools");
        for (String tool : tools) output.append("\n- ").append(tool);
        return output.toString();
    }
}
```

The HTML implementation renders a heading and a list, escaping text-node content. Both products assume their caller supplies valid inputs; public export validation belongs to the creator.

### 5. Select a creator at startup

```java
ReportExport exporter = new HtmlReportExport();
String report = exporter.export("Engineering Tools", List.of("Cameo", "GitLab"));
```

The switch in `main` selects an exporter from the command-line argument. The Factory Method being illustrated is `createFormatter()`, which the inherited `export()` calls through dynamic dispatch.

## Runtime sequence

<FactoryMethodDiagrams kind="sequence" />

The call to `createFormatter()` dynamically dispatches to the concrete creator. The inherited workflow then calls the returned product through `ReportFormatter`.

This implementation creates a fresh formatter per export. Factory Method does not require fresh allocation: an override could return a cached stateless product when its lifecycle contract permits reuse. Products holding files, sockets, or other resources need an explicit ownership and cleanup policy.

The text renderer assumes simple single-line values. HTML escaping handles `&`, `<`, and `>` in text nodes; it is not an attribute escaper or a general-purpose sanitizer. The creator validates shape and presence, not every possible downstream formatting constraint.

## Extend it: add Markdown

Add these nested classes to `FactoryMethodDemo`:

```java
static final class MarkdownReportFormatter implements ReportFormatter {
    @Override
    public String format(String title, List<String> tools) {
        StringBuilder output = new StringBuilder("# ")
                .append(title).append("\n\nTools");
        for (String tool : tools) output.append("\n- ").append(tool);
        return output.toString();
    }
}
static final class MarkdownReportExport extends ReportExport {
    @Override
    protected ReportFormatter createFormatter() {
        return new MarkdownReportFormatter();
    }
}
```

Add a `markdown` branch to startup selection. The inherited export workflow and existing creators stay unchanged. This exercise assumes trusted, single-line Markdown; production rendering needs a deliberate escaping policy.

**Exercise:** create a test-only subclass whose formatter returns a summary such as `Tools: 3`. Verify that it inherits title validation without changing the superclass. Then decide whether constructor-injected formatting would make this application simpler than adding more creator subclasses.

## Verification

`FactoryMethodChecks.java` covers:

- Exact text and HTML results, including empty tool lists and HTML escaping.
- Rejection of blank titles, null values, and unsupported formats.
- A third creator that inherits the workflow and receives an unmodifiable input snapshot.
- A broken factory override returning null.
- Independent repeated exports through the same creator.

## Tradeoffs and common mistakes

| Change or choice | Consequence |
| --- | --- |
| Add a representation | Add a product and creator subclass; update startup selection. |
| Change shared validation | Change the creator workflow once. |
| Change the product contract | Update all formatter implementations. |
| Use inheritance for product selection | Keep workflows reusable, but add subclasses and couple extensions to the creator API. |
| Inject a formatter instead | Favor composition when subclass extension brings little value. |

Avoid hard-coding a concrete product inside the shared workflow, copying the workflow into every subclass, or calling the factory hook during superclass construction. A method named `create` is not evidence of Factory Method unless polymorphic creation is part of the design.

The creator’s validation does not make arbitrary formatter implementations trustworthy. Define their behavioral expectations and test them. Caching a product does not automatically make it thread-safe.

## Related patterns

| Approach | Main variation point | Compared with Factory Method |
| --- | --- | --- |
| Abstract Factory | A matching family of product roles | Usually composes a client with a factory object. Concrete factories can use factory methods internally. |
| Builder | A construction sequence and its result | Collects or performs steps instead of overriding one creation hook. |
| Simple factory | A centralized selection operation | Often uses a conditional; does not require creator subclassing. |
| Static factory method | A named alternative to a constructor | Static methods are not overridden through instance dispatch. |
| Strategy with injection | A supplied behavior | Swaps a collaborator through composition instead of a creator subclass. |
| Template Method | Selected steps of an inherited algorithm | Factory Method can serve as one such step when that step creates a product. |

## A Java API connection

`AbstractCollection` provides shared collection behavior while requiring subclasses to implement `iterator()`. Operations such as `contains` use the iterator supplied by the concrete collection. You can read this as a factory-method role: the collection is the creator and the iterator is the product.

The useful connection is the relationship: shared collection code asks a subclass for an iterator, then uses the returned interface. The collection still defines the iterator’s supported operations and lifetime.

## Choosing this pattern

This fits a framework that already expects subclasses to extend a workflow. If the only variation is which formatter to use, injecting a formatter or a supplier is often simpler. The value here comes from reusing the inherited workflow, not from moving a constructor into a method.
