## The idea in plain English

Mediator coordinates interactions between peer objects so they do not need direct references to each other. A format selector reports a selection change; a mediator chooses and updates the corresponding preview. The selector does not know the preview implementation.

> Move coordination rather than all business logic into the mediator, and keep its collaboration scope explicit.

## The problem before the pattern

If each widget directly updates several other widgets, interactions spread across the UI and become difficult to change. Routing those interactions through a mediator gives coordination rules one visible home.

## Practical use cases

1. Dialogs with interdependent controls.
2. Workflow participants that coordinate through a scheduler.
3. Editors where selection changes update several views.
4. In-process collaboration among components with complex peer rules.

## Java walkthrough

### 1. Report a semantic event

FormatSelector calls the mediator when a format is selected instead of updating a Preview directly.

### 2. Register connections

ExportMediator knows which preview belongs to each selector. Unknown senders fail explicitly.

### 3. Validate coordination rules

The mediator accepts text or HTML and computes preview text before mutating the preview.

### 4. Commit local selection

After successful coordination, the selector records the new format. Unsupported choices leave both states unchanged in this example.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
mediator.formatChanged(this, Objects.requireNonNull(format));
this.format = format;
```

## Extension exercise

Add an ExportButton whose enabled state depends on valid selection. Keep that coordination in the mediator. Define what happens if updating one colleague succeeds and another throws; this synchronous example does not provide rollback for arbitrary peer side effects.

## Verification

MediatorChecks.java verifies: Text/HTML coordination, unsupported choices preserving state, registration requirements, isolation between multiple selector/preview pairs, and null choices.

```bash
cd examples/mediator
javac --release 21 MediatorDemo.java MediatorChecks.java
java MediatorChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Reduced peer coupling | Colleagues simplify, but the mediator can accumulate too much knowledge. |
| Lifecycle | Registration and deregistration must match component lifetime. |
| Coordination | Separate independent interaction groups instead of creating one application-wide mediator. |

This is a synchronous in-memory dialog model, not a UI framework or a message broker. Registration has no disconnect operation and the mediator retains colleagues. It is single-threaded, and callback reentrancy or multi-step peer failure needs deliberate policy in a larger implementation.
