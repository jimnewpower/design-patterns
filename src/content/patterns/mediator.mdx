## How it works

Selecting HTML in an export dialog should update the preview. The selector could call the preview directly, but that approach gets messy once several controls affect one another.

A mediator owns those interaction rules. The selector reports what changed; the mediator finds the corresponding preview and updates it. Each control keeps its own state without carrying references to every peer.

## Why use it

If each widget directly updates several other widgets, interactions spread across the UI and become difficult to change. Routing those interactions through a mediator gives coordination rules one visible home.

## Practical use cases

1. Dialogs with interdependent controls.
2. Workflow participants that coordinate through a scheduler.
3. Editors where selection changes update several views.
4. In-process collaboration among components with complex peer rules.

## Java walkthrough

### 1. Have the selector report a change

`FormatSelector` calls the mediator from `select()`. It has no reference to a preview.

### 2. Connect the controls

`ExportMediator` stores a selector-to-preview mapping. A selector must be registered before it can send a change.

### 3. Resolve the preview content

The mediator accepts text or HTML and computes the display value before calling `Preview.show()`. An unsupported format fails without changing the preview.

### 4. Commit the selection after success

The selector updates its own format only after the mediator returns. In this example, a rejected choice leaves both controls on their previous values.

For example:

```java
mediator.formatChanged(this, Objects.requireNonNull(format));
this.format = format;
```

From the repository root:

```bash

```

## Extension exercise

Add an ExportButton whose enabled state depends on valid selection. Keep that coordination in the mediator. Define what happens if updating one colleague succeeds and another throws; this synchronous example does not provide rollback for arbitrary peer side effects.

## Verification

`MediatorChecks.java` covers text/HTML coordination, unsupported choices preserving state, registration requirements, isolation between multiple selector/preview pairs, and null choices.

```bash
cd examples/mediator
javac --release 21 MediatorDemo.java MediatorChecks.java
java MediatorChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Reduced peer coupling | Colleagues simplify, but the mediator can accumulate too much knowledge. |
| Lifecycle | Registration and deregistration must match component lifetime. |
| Coordination | Separate independent interaction groups instead of creating one application-wide mediator. |

This is a synchronous in-memory dialog model, not a UI framework or a message broker. Registration has no disconnect operation and the mediator retains colleagues. It is single-threaded, and callback reentrancy or multi-step peer failure needs deliberate policy in a larger implementation.

## Choosing this pattern

Give a mediator one collaboration to manage, such as an export dialog. It should know how its controls interact, not become the place every component sends every event. Split it when unrelated workflows start sharing the same coordinator.
