## How it works

Two labels need different text and screen positions, but they may use the same font and size. With enough labels, storing a separate copy of that style for each one can waste memory.

Flyweight shares the style while keeping the text and position on each label. The shared data must be safe to share. Here, `Style` is immutable, and a factory reuses styles with equal font-and-size keys.

## Why use it

Thousands of labels can duplicate identical formatting objects. Putting label coordinates inside a shared style would instead create accidental coupling. Separate state that truly varies per placement from state that can be shared safely.

## Practical use cases

1. Text glyph or style data shared across document positions.
2. Map marker symbols shared across many coordinates.
3. Repeated material or mesh metadata in visualization.
4. Immutable formatting metadata in large reports.

## Java walkthrough

### 1. Choose the state that can be shared

Font and size belong in `Style`. The record is immutable, and both fields participate in equality. A cache key that left out size would reuse the wrong style.

### 2. Reuse styles by their full key

`StyleFactory.get()` builds a key and calls `computeIfAbsent`. An equal key returns the style already in the cache. A different font or size creates another entry.

### 3. Keep placement on the label

Each `Label` stores its own text and y coordinate. It references a shared style, but changing which label is drawn does not change that style.

### 4. Render using both objects

`draw()` reads the label’s placement and the style’s formatting. The labels remain separate even when their style references are identical.

For example:

```java
return cache.computeIfAbsent(key, value -> value);
```

## Extension exercise

Add a color field to Style and to its key. Verify that different colors never share the same flyweight while identical full keys do. Then measure retained memory with many labels before deciding whether this design saves enough to justify a cache.

## Verification

`FlyweightChecks.java` covers identity reuse for equal keys, different instances for different sizes, cache cardinality, independent label placement, and rejection of invalid styles.


The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Memory | Sharing can help with many repeated objects, but keys and cache bookkeeping cost memory too. |
| Immutability | Shared state must be stable or explicitly synchronized; a mutable style can affect every placement. |
| Cache lifetime | Decide bounds, eviction, and concurrency rather than using a global unbounded map by default. |

The factory uses a single-threaded HashMap and retains every requested style for its lifetime. It allocates a candidate key per lookup. This teaching example demonstrates identity reuse; it is not a benchmark or proof of net memory savings.

## Choosing this pattern

First measure whether repeated state accounts for enough memory to matter. Sharing an immutable style can help at scale, but the cache has its own cost and lifetime. Text, coordinates, and other per-placement data should stay outside the shared object.
