## The idea in plain English

Flyweight shares reusable state across many objects to avoid storing the same information repeatedly. Labels have individual text and positions, but can share an immutable font-and-size Style. The style is intrinsic state; text and position are extrinsic state.

> Share only what is intrinsic; the most important line is often the boundary between shared metadata and per-use context.

## The problem before the pattern

Thousands of labels can duplicate identical formatting objects. Putting label coordinates inside a shared style would instead create accidental coupling. Separate state that truly varies per placement from state that can be shared safely.

## Practical use cases

1. Text glyph or style data shared across document positions.
2. Map marker symbols shared across many coordinates.
3. Repeated material or mesh metadata in visualization.
4. Immutable formatting metadata in large reports.

## Java walkthrough

### 1. Identify intrinsic state

Style is an immutable record. Equality includes both font and size, so the cache key covers all shared state.

### 2. Reuse through a factory

computeIfAbsent returns the existing style for an equal key. The example exposes cache size to make reuse observable.

### 3. Keep placement external

Label owns text and its y coordinate. Sharing its style never changes another label position.

### 4. Render with both states

draw combines placement data and style fields. The labels remain distinct objects with intentionally shared metadata.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
return cache.computeIfAbsent(key, value -> value);
```

## Extension exercise

Add a color field to Style and to its key. Verify that different colors never share the same flyweight while identical full keys do. Then measure retained memory with many labels before deciding whether this design saves enough to justify a cache.

## Verification

FlyweightChecks.java verifies: Identity reuse for equal keys, different instances for different sizes, cache cardinality, independent label placement, and rejection of invalid styles.

```bash
cd examples/flyweight
javac --release 21 FlyweightDemo.java FlyweightChecks.java
java FlyweightChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Memory | Sharing can help with many repeated objects, but keys and cache bookkeeping cost memory too. |
| Immutability | Shared state must be stable or explicitly synchronized; a mutable style can affect every placement. |
| Cache lifetime | Decide bounds, eviction, and concurrency rather than using a global unbounded map by default. |

The factory uses a single-threaded HashMap and retains every requested style for its lifetime. It allocates a candidate key per lookup. This teaching example demonstrates identity reuse; it is not a benchmark or proof of net memory savings.
