## How it works

A report starts with a title and a list of tools. Once those choices are set, a builder turns them into text or HTML. The caller can supply each choice by name and ask for the result when it is ready.

The GoF version of Builder also separates the recipe from the output. A director can run the same construction steps against different builders. In Java, you will also see builders used for a single product with many optional settings; those often need no director.

## Why use it

Consider a constructor that grows as report options accumulate:

```java
// Illustrative API: the booleans obscure the caller's intent.
Report report = new Report(title, tools, true, false, true, "html");
```

Overloaded constructors can help at first, but combinations multiply. Setters avoid a long argument list, yet can expose an incomplete object to other code. Format decisions mixed into the assembly logic add another source of change.

Named steps make the call easier to read, and `build()` gives the implementation a place to check required values before returning the result. Validation, copying, and thread safety still need to be implemented.

## Practical use cases

1. **Report or document assembly:** execute a shared recipe while builders produce HTML, text, or another representation.
2. **HTTP requests:** configure a URI, headers, method, and body before creating an immutable request.
3. **Simulation configuration:** choose model inputs, solver settings, and output options, then validate combinations before a run begins.
4. **Test fixtures:** give tests clear defaults and named overrides when a domain object has many meaningful options.

The first case illustrates interchangeable concrete builders. The other cases often use a single fluent builder without a separate director.

## Structure and pattern roles

| GoF role | Java type | Responsibility |
| --- | --- | --- |
| Builder | `ReportBuilder` | Define steps and product retrieval; share validation and construction state. |
| Concrete Builders | `TextReportBuilder`, `HtmlReportBuilder` | Produce a specific report representation. |
| Director | `ReportDirector` | Express the engineering-report recipe without format decisions. |
| Product | `String` | Hold the completed text report or HTML fragment. |
| Client | `BuilderDemo.main` | Choose a builder, invoke the recipe, and retrieve the product. |

Both builders need the same title, tool list, and validation, so they share an abstract base class. They return strings in different formats. Other Builder implementations may return entirely different product types.

## Java walkthrough

### 1. Define construction steps

The shared builder stores a required title and an optional tool list:

```java
abstract static class ReportBuilder {
    private String title;
    private List<String> tools = List.of();

    public final ReportBuilder title(String title) {
        Objects.requireNonNull(title, "title");
        if (title.isBlank()) throw new IllegalArgumentException("Title must not be blank");
        this.title = title;
        return this;
    }

    public final ReportBuilder tools(List<String> tools) {
        this.tools = List.copyOf(tools);
        return this;
    }

    public abstract String build();
    // Protected accessors appear in the complete listing.
}
```

Returning `this` allows method chaining. `List.copyOf` takes a stable view of the supplied tool values, so editing the caller’s list later cannot change the report under construction. It also rejects null lists and entries. The strings themselves can be shared safely.

### 2. Implement the representations

The text builder creates an underlined title and a list. The HTML builder creates a heading and an unordered list, escaping text content.

```java
static final class TextReportBuilder extends ReportBuilder {
    @Override
    public String build() {
        String title = title();
        StringBuilder output = new StringBuilder(title)
                .append("\n").append("=".repeat(title.length())).append("\n\nTools");
        for (String tool : tools()) output.append("\n- ").append(tool);
        return output.toString();
    }
}
```

The protected `title()` accessor throws `IllegalStateException` if no title was supplied. Both concrete builders call it before producing a result. The full listing includes the HTML implementation and both accessors.

The setters collect values; `build()` does the rendering. A builder for a larger object could assemble parts as each step runs.

### 3. Put a reusable recipe in the director

```java
static final class ReportDirector {
    public void constructEngineeringReport(ReportBuilder builder) {
        builder.title("Engineering Tools")
               .tools(List.of("Cameo", "Windchill", "GitLab"));
    }
}
```

The director knows the recipe’s content and steps, but contains no HTML markup or concrete-builder references. It sets both fields each time so this recipe also works predictably with a reused builder.

### 4. Choose the builder and retrieve the product

```java
ReportBuilder builder = new HtmlReportBuilder();
new ReportDirector().constructEngineeringReport(builder);
String report = builder.build();
```

Replace `HtmlReportBuilder` with `TextReportBuilder` to keep the recipe and change the representation. Startup selection still needs to choose a concrete class; the director does not take on that responsibility.

### 5. Build directly when no recipe is needed

```java
String report = new TextReportBuilder()
        .title("Integration Tools")
        .tools(List.of("Cameo", "GitLab"))
        .build();
```

This bypasses the director while preserving validation and representation logic. Introduce a director when a named recipe has enough reuse or complexity to justify it.

## Runtime sequence

<BuilderDiagrams kind="sequence" />

The builder is mutable and not thread-safe. Each `build()` returns an immutable `String` snapshot without clearing construction state. Callers may change steps and build again; earlier products remain unchanged. Create a fresh builder when you need fresh defaults, since omitting a step on a reused builder preserves its previous value.

## Fluent Java builders and the GoF pattern

A typical Java API uses a nested builder for a single immutable product:

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/tools"))
        .timeout(Duration.ofSeconds(10))
        .header("Accept", "application/json")
        .GET()
        .build();
```

Imports for this independent example are `java.net.http.HttpRequest`, `java.net.URI`, and `java.time.Duration`. Constructing the request does not send it.

`HttpRequest.Builder` shows the familiar Java form: configure an object with named methods, then call `build()`. There is one product type and no separate director. The report example goes further by running one recipe against different output builders.

For an immutable product, check combinations of fields in `build()` and copy any mutable input the result will retain. Chaining methods does neither of those things for you.

## Extend it: add a Markdown builder

Place this class inside `BuilderDemo`:

```java
static final class MarkdownReportBuilder extends ReportBuilder {
    @Override
    public String build() {
        StringBuilder output = new StringBuilder("# ")
                .append(title()).append("\n\nTools");
        for (String tool : tools()) output.append("\n- ").append(tool);
        return output.toString();
    }
}
```

Select it in `main` with a `markdown` case. The director and existing builders stay unchanged. This exercise assumes trusted, single-line Markdown text; production Markdown needs escaping rules.

Next, add an optional footer step. Decide its default and whether each representation must render it. Adding a new step affects the builder contract and may require updating every concrete builder; a default no-op is only appropriate if silently omitting that part is acceptable.

**Exercise:** add a second director recipe for a minimal report. If it accepts a reused builder, explicitly set an empty tool list. Verify that a previously populated list does not leak into the minimal recipe.

## Tradeoffs and common mistakes

| Design choice | Benefit | Cost or responsibility |
| --- | --- | --- |
| Named steps | Clear intent at the call site | More types and methods than a simple constructor. |
| Separate director | Reusable construction recipe | Extra indirection; unnecessary for a one-off sequence. |
| Multiple concrete builders | Same recipe, different representations | New steps can affect every implementation. |
| Mutable builder, immutable result | Flexible construction with stable products | Define reuse, defaults, copying, and concurrency explicitly. |

Avoid exposing a partially built product, retaining mutable caller-owned collections, or forgetting validation in one concrete builder. Avoid sharing a builder between threads. Do not assume a reusable builder resets itself after `build()`; document and test the lifecycle.

## Related patterns

| Approach | Main question | Compared with Builder |
| --- | --- | --- |
| Abstract Factory | Which compatible family of collaborators should I create? | Supplies related products; Builder assembles a finished product through steps. |
| Factory Method | Which product should a subclass instantiate? | Provides a creation hook rather than a construction recipe. |
| Prototype | Can I start from a copy of an existing instance? | Reuses existing state rather than collecting construction choices. |
| Constructor or static factory | Can this object be created clearly in one call? | Often preferable when construction is straightforward. |

In the earlier report example, Abstract Factory supplies a heading renderer and a table renderer to a client. Here Builder delivers the report itself. The patterns can cooperate: a builder could use an Abstract Factory internally to obtain compatible components.

## Choosing this pattern

A builder is worth considering when named steps make construction easier to read or when several recipes need the same assembly code. For two required values, a constructor may be clearer. Add a director when there is a recipe to reuse; the fluent Java style does not require one.
