## How it works

One report should sort tool names alphabetically. Another should preserve the order supplied by the caller. Report assembly stays the same in either case.

Strategy extracts ordering into a collaborator. `ToolReport` receives an `Ordering`, uses it, and joins the result. A caller can supply a named implementation or a lambda without changing the report class.

## Why use it

If one report class selects every sorting policy through growing conditionals, algorithm choices and report assembly become coupled. Inject an Ordering strategy so either responsibility can change without editing the other.

## Practical use cases

1. Ordering or scoring policies for reports.
2. Routing algorithms chosen by application configuration.
3. Pricing calculations with explicit business policies.
4. Simulation solver selection behind a stable algorithm contract.

## Java walkthrough

### 1. Define what the policy receives and returns

`Ordering` takes tool names and returns them in the chosen order. The context copies input before handing it over.

### 2. Implement the two policies

`Alphabetical` sorts with Java’s natural string order. `AsProvided` returns the values in their supplied order.

### 3. Use the result in the report

`ToolReport` checks the returned list and joins its names. It does not contain a format flag or an ordering conditional.

### 4. Supply another implementation

The reverse-order test uses a lambda. A separate class is useful when the algorithm needs a name or state, but the contract works with either form.

For example:

```java
List<String> ordered = List.copyOf(ordering.order(List.copyOf(values)));
```

## Extension exercise

Add a case-insensitive ordering policy and explicitly define tie order. If the algorithm must preserve the input multiset, add contract tests ensuring custom strategies never drop or duplicate values. The current context checks nullability, not that stronger invariant.

## Verification

`StrategyChecks.java` covers alphabetical order with duplicates, preserved supplied order, empty input, reverse lambda substitution, non-mutation of caller data, and invalid strategy input/output.

```bash
cd examples/strategy
javac --release 21 StrategyDemo.java StrategyChecks.java
java StrategyChecks
```

The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Composition | Algorithms vary without subclassing the context, but clients must select an appropriate one. |
| Contract consistency | Strategies should agree on inputs, side effects, and result guarantees. |
| Simple algorithms | A lambda may be clearer than a named class; an interface still documents the role. |

Natural string ordering is case-sensitive and is not locale-aware collation. The context fixes its strategy at construction. Strategies are trusted to fulfill their algorithm contract; no runtime proof of permutation or optimality is attempted.

## Choosing this pattern

Use a strategy when callers should choose a policy without changing the context. Keep the behavioral contract precise enough that implementations can be substituted. If the algorithm is a one-liner, a lambda may be more readable than another named class.
