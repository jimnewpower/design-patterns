## The idea in plain English

Strategy makes alternative algorithms interchangeable behind one contract. A tool report can preserve supplied order or sort alphabetically. The report delegates ordering and keeps its own job of joining the resulting names.

> Interchangeability is a behavioral promise, not just a matching method signature.

## The problem before the pattern

If one report class selects every sorting policy through growing conditionals, algorithm choices and report assembly become coupled. Inject an Ordering strategy so either responsibility can change without editing the other.

## Practical use cases

1. Ordering or scoring policies for reports.
2. Routing algorithms chosen by application configuration.
3. Pricing calculations with explicit business policies.
4. Simulation solver selection behind a stable algorithm contract.

## Java walkthrough

### 1. Define a precise algorithm contract

Strategies return tool names in their chosen order. Inputs are validated and copied by the context.

### 2. Implement interchangeable policies

Alphabetical sorts by Java natural String ordering. AsProvided preserves input order; both return stable lists.

### 3. Delegate from context

ToolReport supplies a defensive input snapshot, validates the returned list, and joins it.

### 4. Substitute without a context edit

A lambda can implement the functional strategy contract, as the reverse-order test demonstrates.

The key collaboration is visible here (imports and surrounding types are in the complete listing):

```java
List<String> ordered = List.copyOf(ordering.order(List.copyOf(values)));
```

## Extension exercise

Add a case-insensitive ordering policy and explicitly define tie order. If the algorithm must preserve the input multiset, add contract tests ensuring custom strategies never drop or duplicate values. The current context checks nullability, not that stronger invariant.

## Verification

StrategyChecks.java verifies: Alphabetical order with duplicates, preserved supplied order, empty input, reverse lambda substitution, non-mutation of caller data, and invalid strategy input/output.

```bash
cd examples/strategy
javac --release 21 StrategyDemo.java StrategyChecks.java
java StrategyChecks
```

Failures throw `AssertionError`; no `-ea` flag is needed. CI also compares the demo’s actual console output against the checked-in `expected.txt`. These checks exercise observable behavior rather than merely counting classes.

## Tradeoffs and implementation limits

| Concern | Design judgment |
| --- | --- |
| Composition | Algorithms vary without subclassing the context, but clients must select an appropriate one. |
| Contract consistency | Strategies should agree on inputs, side effects, and result guarantees. |
| Simple algorithms | A lambda may be clearer than a named class; an interface still documents the role. |

Natural string ordering is case-sensitive and is not locale-aware collation. The context fixes its strategy at construction. Strategies are trusted to fulfill their algorithm contract; no runtime proof of permutation or optimality is attempted.
