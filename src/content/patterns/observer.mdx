## How it works

A release can matter to several parts of an application: a view may refresh, an audit listener may record it, and a status panel may display it. The publisher should not need a hard-coded call to each one.

Observer lets those consumers subscribe. The publisher sends an event to the registered callbacks, and consumers can unsubscribe when they no longer need updates. How and when those callbacks run is part of the contract.

## Why use it

Calling every concrete notification consumer from the release publisher couples it to dashboards, audit views, and other optional behavior. Subscriptions let those consumers join and leave without changing the publisher.

## Practical use cases

1. UI views updating after model changes.
2. In-process release or configuration notifications.
3. Optional audit or metrics listeners.
4. Decoupled reactions to domain events within one process.

## Java walkthrough

### 1. Register a callback

`subscribe()` stores the listener under a unique token. Registering the same callback twice creates two subscriptions.

### 2. Return something the caller can close

The returned handle removes that token. Closing it twice is harmless. The demo uses try-with-resources to tie the subscription to a scope.

### 3. Choose recipients before delivery

`publish()` snapshots the current listeners. A callback can unsubscribe another listener, but that removal takes effect on the next event.

### 4. Call listeners in order

Delivery runs synchronously in registration order. The first callback exception stops delivery and reaches the publisher’s caller.

For example:

```java
for (Consumer<String> listener : List.copyOf(listeners.values())) listener.accept(name);
```

## Extension exercise

Change exception handling to attempt every listener and aggregate failures. Write tests proving the chosen delivery guarantee. For asynchronous delivery, define executor ownership, ordering, queue bounds, and shutdown before replacing direct calls with background tasks.

## Verification

`ObserverChecks.java` covers registration order, unsubscribe and double-close, no-listener publication, changes during snapshot delivery, fail-fast listener exceptions, and null listeners/events.


The checks throw `AssertionError` on failure. The console output is also checked against `expected.txt`.

## Tradeoffs

| Decision | What to consider |
| --- | --- |
| Decoupling | Publisher does not know concrete consumers but delivery can be harder to trace. |
| Lifecycle | Unsubscribe reliably to prevent retained listener graphs. |
| Delivery contract | Ordering, exceptions, reentrancy, and thread choice are part of the API. |

This subject is single-threaded and synchronous. It provides no persistence, retry, exactly-once delivery, backpressure, or cross-process messaging. Listeners are strongly retained until removed. Reentrant publication is not blocked and can recurse; define a policy if callbacks can publish again.

## Choosing this pattern

The subscription API is only the beginning. Decide ordering, exception handling, callback threads, and when removal takes effect. For a small synchronous subject, explicit handles and a documented failure policy are often enough.
